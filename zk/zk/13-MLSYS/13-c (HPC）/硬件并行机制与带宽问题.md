首先我们来看一个程序样例:
对包含N个浮点数的数组的每个元素
使用泰勒展开计算sin(x) : sin(x) = x - x^3/3! + x^5/5! - x^7/7! + ...
```
void sinx(int N, int terms, float* x, float* result) { 
	for (int i=0; i<N; i++) {
	    float value = x[i]; 
	    float numer = x[i] * x[i] * x[i];
	    int denom = 6;// 3! 
	    int sign = -1; 
		
	    for (int j=1; j<=terms; j++) { 
		    value += sign * numer / denom;
		    numer *= x[i] * x[i];
		    denom *= (2*j+2) * (2*j+3);
		    sign *= -1; 
		}
		 
		result[i] = value; 
	} 
}
```
指令级并行 (ILP) 有可能实现每个时钟解码并执行两条指令，前提是编译出来的程序中存在可以并行，依赖性没那么强的指令。
但是，这里是有一部分指令是不能并行的，难以做ILP。

这个大约是2005年前？但是很明显，这条路子会碰到功耗墙以及ILP的问题。
![L02-01 Basic Architecture and Programming, p.12](files/slides/hias-parellel/L02-01%20Basic%20Architecture%20and%20Programming.pdf#page=12&rect=0,0,720,540)

> 想法 #1: 使用增加的晶体管来为处理器添加更多内核

使用增加的晶体管来为处理器添加更多内核,而不是使用晶体管来增加加速单个指令流的处理器逻辑的复杂性 (e.g., out-of-order and speculative operations)
![L02-01 Basic Architecture and Programming, p.13](files/slides/hias-parellel/L02-01%20Basic%20Architecture%20and%20Programming.pdf#page=14&rect=0,0,720,540)

但是，上文中我们编写的，这个用gcc编译的程序只会作为一个线程在处理器内核之一上运行。
如果每个较简单的处理器内核都比原来的单个复杂处理器内核慢25% ，那么我们的程序现在运行速度会慢 25%. :-(

所以，我们可以使用Posix标准线程库pthreads重新编写程序体现并行性。
```cpp
typedef struct {
    int N;
    int terms;
    float* x;
    float* result;
} my_args;

void parallel_sinx(int N, int terms, float* x, float* result)
{
    pthread_t thread_id;
    my_args args;

    args.N = N/2;
    args.terms = terms;
    args.x = x;
    args.result = result;

    pthread_create(&thread_id, NULL, my_thread_start, &args); // launch thread
    sinx(N - args.N, terms, x + args.N, result + args.N); // do work
    pthread_join(thread_id, NULL); // wait for thread end
}

void my_thread_start(void* thread_arg)
{
    my_args* thread_args = (my_args*)thread_arg;
    sinx(args->N, args->terms, args->x, args->result); // do work
}
```

或是，使用数据并行表达(在我们虚构的，仅作例子的数据并行语言中，使用虚构的`forall`提醒编译器生成并行指令)
程序员声明的循环迭代是独立。的有了这些信息，你可以想象编译器如何自动生成并行线程代码
```cpp
void sinx(int N,int terms,float* x,float* result){
	// declare independent loop iterations 
	forall (int i from 0 to N-1){
	.....
	}
}
```
所以只要你程序编写得当，核数够多，我们可以并行计算16个元素。

## SIMD

```cpp
void sinx(int N,int terms,float* x,float* result){
	// declare independent loop iterations 
	forall (int i from 0 to N-1){
	.....
	}
}
```
此代码的另一个有趣属性是: **并行性跨越循环的迭代**。循环的所有迭代都做同样的事情，都有相同的指令去计算单个输入数的
正弦值，只不过输入的`x[i]`不同。

既然只有输入不同，指令做的事都是相同的，那么我们可否添加ALU提高计算能力的同时，只使用相同的指令去操控一大堆ALU?毕竟我们只有输入不同，指令是相同的。

> 想法 #2: 添加 ALU 以提高计算能力,分摊管理跨多个 ALU 的指令流的成本/ 复杂性

这就是SIMD处理的概念。 ==Single instruction, multiple data 单指令==
多数据向所有 ALU 广播相同的指令在所有 ALU 上并行执行

![](../../../../files/images/MLsys/13-c/13-b-1-6.png)

SIMD之后，我们该怎么做呢？可以Intel提供的SIMD函数接口**AVX  intrinsics**
1. 这是一种纯C语言，良好的交互接口 
2. 需要手工向量化实现并行操作 
3. 可以去Intel intrinsics Guide官网查询
 intrinsics函数操作的是含有8个32-bit数的向量，例如8个float的vector。
 这里，就是使用 256 位向量寄存器上的向量指令同时处理 8 个数组元素。所以循环的步长为8。
![02_basicarch_xX3ssOi, p.40](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=40&rect=0,0,1920,1080)

所以SIMD+多核，我们的计算能力一下爆发式增长，可以比原来单核单线程多整整128倍！

### SIMD中的条件执行

还是这段代码：
```cpp
void sinx(int N,int terms,float* x,float* result){
	// declare independent loop iterations 
	forall (int i from 0 to N-1){
	.....
	}
}
```

这里在程序中使用 "forall" 是向编译器声明：循环的各次迭代是相互独立的，并且相同的循环体将在大量数据元素上执行。
这种抽象可以促进自动生成同时包含多核并行代码和向量指令的代码，从而利用核心内的 SIMD 处理能力。

如果遇到条件执行的语句会怎样？在这种情况下，ALU会屏蔽（丢弃）输出，并不是所有的 ALU 都能做有用的工作。最坏情况下只会有1/8的peak performance。在cuda中，你也可以见到[分支发散](../13-a%20(CUDA)/CUDA编程/13-a-6（线程束Warp）.md#SM与SIMT)的情况。
![](../../../../files/images/MLsys/13-c/13-b-1-8.png)


显然，指令一致是最好的，性能最优。如果发生发散，性能会降低。
多核 CPU不怕发散，因为每个核有独立的Fetch/Decode，可以各走各的。
SIMD 单元最怕发散，因为它们共享一个Fetch/Decode，一旦发散就得串行化（Masking），效率大跌。
![L02-01 Basic Architecture and Programming, p.33](files/slides/hias-parellel/L02-01%20Basic%20Architecture%20and%20Programming.pdf#page=33&rect=0,0,720,540)

CPU 上的 SIMD是**Explicit显式**的。编译器在编译阶段就把代码变成了“向量指令”（比如 `vmulps` 一次算 8 个乘法）。
你可以手写（Intrinsics，很难），也可以用高级语言（ISPC/forall，容易），或者指望编译器自动优化（Auto-vectorization，不可靠）。
![L02-01 Basic Architecture and Programming, p.34](files/slides/hias-parellel/L02-01%20Basic%20Architecture%20and%20Programming.pdf#page=34&rect=0,0,720,540)

---

隐式 SIMD (Implicit SIMD)中，编译器生成的是包含**标量指令**（Scalar instructions）的二进制文件。
但是，处理器上总是会有 N 个程序实例（线程）一起运行。
硬件（而不是编译器）负责在 SIMD ALU 上，针对不同的数据，同时执行来自多个程序实例的**同一条指令**。

这讲的是 **GPU 上的 SIMD**（NVIDIA 称之为 SIMT）。
*   它是**Implicit隐式**的。你写 CUDA 代码时，看起来像是在写一个普通的串行程序（标量指令）。
*   GPU 硬件会在运行时，把 32 个线程捆绑在一起（Warp），强行让它们执行同一条指令。
*   如果这 32 个线程遇到了 `if-else` 分歧（Divergence），硬件就必须让一部分人暂停，效率就会暴跌（最惨跌到 1/32）。

## Multi-thread

> 访存已经成为处理器提升算力的瓶颈

为什么我们需要Cache?
当处理器的运行指令流中出现了：后一条指令依赖于前一条指令，前一条指令迟迟无法完成，处理器就会 Stall
==而访问内存是停顿的主要来源==，访存要100个cycle，而计算只需要1个cycle。
所以很明显，Cache能够减少处理器Stall的时间，这是减少Stall的第一种手段。

第二，我们也可以通过数据预取Stall。
![L02-01 Basic Architecture and Programming, p.44](files/slides/hias-parellel/L02-01%20Basic%20Architecture%20and%20Programming.pdf#page=44&rect=0,0,720,540)

但是，假设下一步需要的数据没有读取过，cache里没有，而且代码类似：
```cpp
int x = some_function(); 
int y = A[x];
```
y难以使用预取手段。此时，我们怎么办？

> 第三种方法：在同一核心上交错处理多个线程以隐藏停顿

与预取一样，多线程是一种延迟隐藏，而不是减少延迟的技术。
一个线程访存卡住Stall了，我们立马切到下一个线程去，核里有完整的上下文可供切换。访存好的线程会进入Runnable状态等待核的调度。
![02_basicarch_xX3ssOi, p.66](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=66&rect=0,0,1920,1080)

这是面向吞吐量系统的核心思想: 可能会增加单体线程运行完成的时间，但能够提升多个线程时同时运行时整体系统的吞吐量
为什么会增加单体线程的运行时间？因为可能这个线程访存好后是Runnable状态，但它没有被处理器执行。 此时核心正在运行其他线程，这个Runnable状态的核正在等待调度。
![02_basicarch_xX3ssOi, p.67](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=67&rect=0,0,1920,1080)

不过，一个核内用来储存Exectution Context的内容是有限的。假设你设计Core有4个Execution Context，那么其的Context可储存的内容就多，但是可以用来切换的线程数就少， latency hiding ability低一些。如果设计16个则正好相反，可用来切换的线程数就多，latency hiding ability高，Context可储存的内容就少。

多线程的理论总结如下：
![L02-01 Basic Architecture and Programming, p.54](files/slides/hias-parellel/L02-01%20Basic%20Architecture%20and%20Programming.pdf#page=54&rect=0,0,720,540)

一个拥有多个硬件线程的处理器，有能力通过执行**其他线程**的指令来避免停顿 (stalls)，即当某一个线程必须等待一个长延迟操作（如读取内存）完成时，处理器转而去干别的。
注意：多线程并不会改变内存操作本身的延迟（读内存该慢还是慢），它只是让这种延迟不再导致处理器利用率的降低。

多线程处理器通过执行其他线程的**算术运算**来掩盖内存延迟。
那些“每次内存访问对应更多算术运算”（即计算密度更高）的程序，只需要较少的线程就能掩盖住内存停顿。
如下图，如果一个线程执行所需的cycle数是3，就需要5个线程来彻底掩盖Stall。
![02_basicarch_xX3ssOi, p.78](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=78&rect=0,0,1920,1080)

## SIMT intro

这是一个GPU streaming multi-processor (SM)核的架构，这里的小黄色框是simd单元。
为什么每个 warp 每个时钟周期处理 32 个数据，而这里使用的是 16 的 SIMD ALUs?
因为ALU 的运行时钟速率是芯片其余部分的两倍。因此，每条解码指令在16 SIMD ALU运行两个时钟就可以处理 32 条数据（但对程序员来说，它的行为就像一个 32 位宽的 SIMD 操作）。
NVIDIA V100有80个SM，可以尽情地掩盖latency。
![02_basicarch_xX3ssOi, p.85](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=85&rect=0,0,1920,1080)


许多现代 GPU 执行的硬件线程，运行的是只包含**标量指令**的指令流，并不是在操作vector，只是操作的线程数够多，有simd-width个，看起来很像simd。
GPU 核心会检测不同的硬件线程何时在执行**同一条指令**，并利用 SIMD ALU来实现simd-width个线程的**同时执行**。
在这里，ALU 6 将会被masked off，因为线程 6 没有像其他硬件线程那样执行同一条指令。相当于发散执行了。

## Superscalar execution, SIMD execution, Multi-core execution, and hardware multi-threading

所以我们可以看出，要充分发挥这些并行硬件的全部性能，我们编写程序，设计流程时应该：
1.  拥有**充足的并行工作**，以利用所有可用的执行单元（涵盖许多核心，以及每个核心内的许多执行单元）。
2.  成组的并行工作项必须需要相同的指令序列（以便利用 SIMD 执行）。
3.  暴露比处理器 ALU 数量更多的并行工作，以便通过交错执行工作来**掩盖内存停顿**。

这是一个只有两路超标量的核，可以玩两路的ILP指令级并行，两路操作的都是scalar标量。
![02_basicarch_xX3ssOi, p.94](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=94&rect=0,0,1920,1080)

将其与simd技术结合，我们同样可以做两路指令级并行，只是一路是scalar 标量的，另一路操作的是vector向量。
![02_basicarch_xX3ssOi, p.96](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=96&rect=0,0,1920,1080)

这里则是结合了超标量，simd以及多线程技术，而且这里用了==SMT技术==，来自不同线程的指令可以同时运行。
这意味着在**同一个时钟周期**内，CPU 可以从 **Stream 0** 拿一条向量指令（给向量 ALU），同时从 **Stream 3** 拿一条标量指令（给标量 ALU）。
这极大地提高了硬件利用率。如果线程 0 只有向量活干，线程 3 只有标量活干，它俩正好互补，把 CPU 填满。
SMT技术与之前介绍的多线程技术不同，其同一时刻可以服务多个线程。原来的多线程如果当前线程ILP并行度不够，硬件会闲置，SMT可以用其他线程的指令填补闲置的硬件单元。
SMT对调度器要求高，调度器要从 4 个线程里挑出互不冲突的指令组合。现代的CPU基本都有这种技术。
![02_basicarch_xX3ssOi, p.99](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=99&rect=0,0,1920,1080)

再将上述技术与多核结合起来，则如下图，单核四线程，两路超标量。
![02_basicarch_xX3ssOi, p.100](files/slides/CS149/02_basicarch_xX3ssOi.pdf#page=100&rect=0,0,1920,1080)


如下，假设你写了一个 C 应用程序，它生成了**两个**线程。
该应用程序运行在如下图所示的处理器上：两个核心，每个核心有两个执行上下文（硬件线程），每个时钟周期最多执行两条指令，其中一条是 8 宽度的 SIMD 指令。

谁负责将应用程序的线程映射到处理器的execution contexts？答：操作系统 (OS)

问题：如果你正在实现操作系统，你会如何将这两个线程分配给这四个执行上下文？
答：理论上一个放在Core0,一个放在Core1性能最好。但是要考虑通信问题。

另一个问题：如果你的 C 程序生成了**五个**线程，你会如何将线程分配给执行上下文？
答：使用OS的上下文切换，让OS去做线程调度（用时间片轮转或是其他什么调度技术，毕竟线程坑位不够）。

## What is Bandwidth and latency?

带宽和延迟这两个概念要分清。我们在下面用一个例子来解释。假设这段公路的长度为50km。
则可知，任何车辆从起点到终点的时间都是半个小时，这就是延迟。
而带宽则是面向吞吐量的概念，也就是每单位时间能有多少车到达终点。也即是:The rate at which the memory system can provide data to a processor
![03_multicore2-ispc, p.10](files/slides/CS149/03_multicore2-ispc.pdf#page=10&rect=0,0,1920,1080)

X要读 64 字节，但内存每周期只能给 **8 字节**。读完 X 需要 8 个时钟周期 (64 / 8 = 8)。每时钟周期能做 1 次数学运算。
在这 8 个周期里，当前线程的后续指令（2 和 3）完全无法执行（Stall）。
![03_multicore2-ispc, p.17](files/slides/CS149/03_multicore2-ispc.pdf#page=17&rect=0,0,1920,1080)

可以看到读取内存的时间太长，计算单元不停的Stall。
![03_multicore2-ispc, p.18](files/slides/CS149/03_multicore2-ispc.pdf#page=18&rect=0,0,1920,1080)

在稳态下，核心利用率不足 (core underutilization) 仅仅与指令吞吐量和内存吞吐量的相关，而与内存延迟或未完成内存请求数量无关。计算使用数据的速度远比传输的速度快。
![03_multicore2-ispc, p.20](files/slides/CS149/03_multicore2-ispc.pdf#page=20&rect=0,0,1920,1080)

我们从带宽与延迟的角度去理解CPU内部的指令流水线就能看出，明显延迟是4个cycle，在流水线的加持下，吞吐量是
1 instruction per cycle。当然这是一个简陋的示例，现代CPU的流水线深度大概20个stages。

如果处理器以过高的速率请求数据，则内存系统无法跟上，再多的延迟隐藏也无济于事。克服带宽限制是应用程序开发人员在吞吐量优化系统上面临的共同挑战。
由于现代芯片的高算术能力，许多并行应用程序（在 CPU 和 GPU 上）都受到访存带宽限制。GPU 架构使用与 CPU 相同的提高计算吞吐量的思想，但 GPU 将吞吐量推向了极致。
