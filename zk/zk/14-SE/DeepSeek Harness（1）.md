# DeepSeek Harness（1）

上一讲把工作区看成状态，把 Agent 的工作看成状态迁移，再通过 CI/CD 检查、交付变化。这一讲把问题落到 DeepSeek Harness（简称 dsh）：**一个能够工作的 Agent Loop，怎样成为能够恢复、交互、扩展，并承受需求变化的产品？**

Harness 不只是把模型接到工具上，而是模型周围的运行与协作环境。模型调用、执行控制、会话历史、工具、权限和界面必须形成共同规则。核心问题不是“还差几个功能”，而是：新增功能究竟应当落在哪里，能否复用已有机制，而不必反复改写整个循环？

## 150 行的 Agent，不等于可靠的产品

### 能完成任务，不代表能够承担任务

最小 Agent 的循环很直接：接收目标，把上下文交给模型，执行模型提出的工具调用，把结果放回上下文，再请求下一步。循环虽然短，却能调动已有工具完成复杂工作。

课程以“生成一个相对真实的南大仙林校区 3D 图”为例。建筑和道路轮廓来自 OpenStreetMap，程序转换坐标、生成楼体，补充道路、水域、绿地和相机交互。这里的“相对真实”有边界：空间布局有数据依据，缺失的高度和部分景观则采用估计或示意，不能理解成逐栋实测的数字孪生。

![最小 Agent 可以生成复杂结果，却仍然依赖未被处理的运行假设](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=4&rect=0,0,960,540&width=960)

真正反驳“它完全可以工作”的，是网络或服务中断后程序直接退出。演示只要求在理想条件下跑通；产品却要求用户把工作交出去后，即使出错也知道发生了什么，还能合理继续。**可靠恢复是需求带来的本质复杂性，不会随着主循环缩短而消失。**

### 先分类错误，再决定是否重试

| 情形 | 正确方向 | 不应采取的做法 |
|---|---|---|
| 暂时断网、服务限流 | 保存进度，有限重试，显示等待原因 | 无限重试或丢掉上下文从头开始 |
| 输入损坏、权限不足 | 说明受阻对象，请求修复输入或调整授权 | 原样重复调用，期待条件自己改变 |
| 操作结果未知 | 核实实际状态，再决定继续、补偿或重试 | 把没有返回成功当作没有执行 |

最危险的不是明确失败，而是执行和确认之间的缝隙。文件已经移动，结果还没进入记录，进程就崩溃了。恢复后直接再做一次，可能覆盖目标，或把原路径消失误判成另一项错误。

![未收到结果不等于没有执行，恢复必须面对外部状态](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=5&rect=0,0,960,540&width=960)

因此，“接着做”必须先判断真实世界。幂等性要求同一逻辑操作重复提交，不产生额外业务效果；稳定操作标识、执行结果记录和重复请求识别可以协助实现，但标识记录与实际修改也必须协调。只登记“已完成”而没有完成修改，或者修改完成却没有记录，都留下恢复漏洞。

这条边界贯穿全讲：**重建内部状态，不等于重新执行外部副作用。** 回放会话可以重新得到任务视图，不能因此再次移动文件、扣款或发信。

## 把“帮我做事”写成可验收的产品行为

### 交付物，而不是成功描述

Slides 中的办公 Agent 规格把需求分成执行控制、交付验收、隐私诊断和使用体验。内嵌 PRD 进一步说明：用户要的是可编辑、能打开、内容经过核对的成果，而不只是聊天框里的建议。

以整理项目周报为例，产品要读取指定资料，核对日期和项目，标明冲突，生成 DOCX。负责人缺失时应标记待确认，不能补出一个人名。工具调用计划、模型声称成功、文件名已经出现，都不足以证明交付完成；必须检查文件存在、格式可读、必需内容完整，数值与来源能够追溯。

![围绕执行控制、交付验收和权限展开的产品需求](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=6&rect=0,0,960,540&width=960)

“部分完成”也应是明确结果：哪些内容已经可用，哪些目标没有完成，继续还缺什么条件。否则，一个受限网站或损坏附件就容易被模型的流畅措辞掩盖。

### 中途控制是一组状态迁移

用户补充“只分析第三季度”，产品需要找出受影响步骤，重算相关结果，保留仍然有效的工作，并形成新版本。暂停、停止与恢复也不是同一个动作：

- **暂停**：保存检查点，不再启动新步骤，等待恢复。
- **停止**：结束本次运行，保留已有成果与记录；已经完成的文件修改不会自动撤销。
- **恢复**：重新检查授权、输入版本和外部状态，不能盲目从旧位置继续。

在途工具调用还可能暂时无法取消。界面显示“已停止受理”，不能被混同为所有外部动作已经终止。PRD 将停止后的新调用边界和在途状态分别规定，正是为了让按钮含义可以测试。

### 预算、权限和同步不是附属设置

预算要计量模型请求、工具次数和执行时间，重试也会消耗额度；到达上限后保存进度并暂停，不能擅自增加预算。PRD 中的数值是需求基线，不是 dsh 已测得的能力，也不是所有 Agent 的通用参数。

权限要区分读取、创建、修改和外发。批准读取目录，不等于批准覆盖文件；网页中的命令，也不构成用户授权。约束必须进入工具检查、执行环境和数据外发规则，不能只靠提示词。批准后的对象或文件版本改变，原确认也可能失效。

历史、同步和备份则把问题拉长：窗口关闭后任务是否继续，重启能恢复到哪里，其他设备看见什么，用户手工修改后的文件与旧检查点如何协调？这些需求围绕同一任务交叉发生。如果每个按钮各维护一份状态，产品就会在本质复杂性之外，再制造一层同步的附带复杂性。

### 回到图里：真实需求包围的是同一个循环

![恢复、暂停改需求、权限、预算、验收与同步共同围绕最小 Agent Loop](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=7&rect=0,0,960,540&width=960)

左侧是“上下文 → 调用模型 → 执行工具 → 结果加入上下文”的最小循环；没有工具调用时，回答用户并结束本轮。右侧的六项需求并没有构成六个独立产品，而是同时作用于左边的执行过程。

例如，“最多花 20 分钟”要在重试与新步骤启动时检查，“这份文件别碰”要在真正执行工具时约束，“换台设备接着做”又依赖同一轮任务留下可恢复的事实。图的意义在于说明：主循环可以很小，但围绕它的执行边界必须一致，不能靠互不相通的按钮状态拼起来。

## 需求不仅增加，还会改变方向

原来的产品可能围绕“打开项目，完成一次编码任务”设计。课堂用 Grok Bot 引出另一种预期：用户想要论文晨报、每日新闻、持续值守的助手，以及不同角色之间的协作。模型未必更换，产品的时间结构和组织方式却变了。

![Bots 带来的变化不是多一个按钮，而是新的持续工作方式](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=8&rect=0,0,960,540&width=960)

讲义以 dsh-bot 的不同 Bot 配置、定时例程和相互通信说明扩展的可能性，也提到执行、审阅、改进角色的接续工作。重点不是宣称某个团队一定比另一个团队快，而是比较变化穿透的范围：新交互能否复用 Session、模型执行与工具，还是必须从入口一路修改到主循环？

![dsh-bot 用不同 Bot 与会话呈现新的工作组织方式](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=9&rect=0,0,960,540&width=960)

这张产品画面应与上一页“需求改变”一起理解：变化不仅是换皮肤，还包括谁发起任务、任务何时运行、结果交给谁。若这些差异能够通过新的插件和配置表达，原有的会话、执行与工具能力便可以复用；若它们已写死在编码助手的入口里，新形态就会迫使核心代码大面积改变。画面本身不是开发速度或系统可靠性的测量。

## 架构：用受限换便利，但假设有有效期

### 从仓库入口开始约定架构

![项目起点就用 AGENTS.md 链接 MVP 需求与微内核架构说明](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=10&rect=0,0,960,540&width=960)

Slides 回看项目起点时，列出的不只是初始化 README，还包括建立 `AGENTS.md`、链接 MVP 需求分析与微内核架构文档。这与上一讲的“知识可发现”相接：先让后来参与的 Agent 找得到目标与边界，才可能让不同轮次的实现沿着同一套约定演进。入口文档不是功能完成的证据，但它能减少每轮重新猜测设计的成本。

### 接受一种表达方式，获得一类基础能力

架构不是无条件的自由。它规定对象、接口与协作方式，排除一些实现选择，换来隔离、复用、测试、日志或恢复。是否值得，取决于这些限制与需求是否吻合。

![架构固定部分选择，把一类工作交给基础设施](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=11&rect=0,0,960,540&width=960)

| 代表架构 | 接受的约束与获得的便利 | 需求变化后暴露的边界 |
|---|---|---|
| 操作系统进程 | 在自己的地址空间执行，通过系统调用访问资源；获得隔离和调度 | 地址独立不代表资源无限，内存不足和资源竞争仍影响可靠性 |
| Java 等托管语言 | 遵守对象、类型与引用规则，把布局和回收交给运行时 | 实时互动可能受到分配速率、GC 暂停和 CPU 开销影响 |
| 典型 LAMP 应用 | 按请求、业务逻辑、数据库组织处理；复用事务和持久化设施 | 持续在线协作需要重新安排长连接、共享状态与后台任务 |
| Event Sourcing | 记录发生过的事实，从事件推导状态；获得审计和重建依据 | 历史规则、外部输入与副作用不能靠事件列表自动解决 |

下面四个例子都沿着“接受什么约束 → 得到什么便利 → 哪个前提可能失效”来读。架构的价值不在于隐藏一切细节，而在于让一类细节由共同基础设施处理；当需求越过它的边界，使用者仍然要重新面对这些细节。

### 操作系统：地址空间独立，物理资源并不独立

![进程接受地址空间和系统调用约束，物理内存不足仍会暴露出来](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=14&rect=0,0,960,540&width=960)

进程不能随意访问其他进程的内存，而要通过自己的地址空间与系统调用工作。限制换来隔离和调度：编辑器、编译器和播放器不必各自管理整台机器，一个进程的非法访存也不应直接改坏另一个进程的地址空间。

但“自己的地址空间”不等于无限物理内存。活跃数据超过可用内存时，频繁换页可能让系统忙于搬数据；程序放进有内存限额的环境，也可能触及上限而被终止。程序逻辑没变，运行条件却变了，资源容量与竞争就重新进入上层判断。隔离隐藏了部分管理细节，没有消灭硬件约束。

### 高级语言：回收交给运行时，延迟仍需取舍

![托管语言简化内存管理，实时互动会重新暴露分配与 GC 成本](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=15&rect=0,0,960,540&width=960)

Java 等托管语言要求按对象、类型与引用规则写程序，把对象布局和回收交给运行时。实现普通课程论坛时，开发者可以集中处理帖子与评论，不必逐个安排对象何时释放。

论坛加入实时互动后，大量短命对象可能让 GC 暂停与 CPU 开销进入用户可感知的延迟。此时降低暂停、提高吞吐和减少内存占用存在取舍，需要重新观察分配速率、活跃对象与堆大小。这不是说 Java 无法低延迟运行，而是“运行时会处理”不能代替对具体负载的分析。

### LAMP：一次请求内的事务，不覆盖整个协作世界

![从表单请求扩展到长连接与外部支付时，LAMP 的分工边界显现出来](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=16&rect=0,0,960,540&width=960)

典型表单网站把操作组织成“HTTP 请求 → PHP 处理 → MySQL 读写 → 返回页面”。选课时的名额检查与报名记录可以放进同一数据库事务，Web 服务、持久化与备份也有现成设施。

新增实时讨论后，如果 PHP-FPM 请求一直等待消息，就会持续占用工作进程；系统需要重新安排长连接、共享状态与后台任务。这不意味着 LAMP 完全无法实时交互，而是原有的一次请求模型不再包办全部协作。再加入外部支付，数据库回滚也不能自动撤销已经完成的扣款，重试、去重与补偿必须在跨系统边界上重新定义。

### Event Sourcing：能够重建状态，不代表可以重做动作

![事件历史提供审计与重建，外部副作用和历史规则仍需单独处理](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=17&rect=0,0,960,540&width=960)

校园卡记录“充值 100 → 消费 12 → 退款 12”，便能从同一份历史计算余额、生成流水，并解释数字的来由。代价是不能随意覆写结果；纠错也需要留下发生了什么的记录。

但回放消费记录应当重算余额，不能再次真实扣款；历史外币消费也不能按今天的汇率重新解释。事件格式、规则版本和当时的外部输入都影响重建结果。这个例子直接铺垫后文的 Session：共享一份事实有助于避免状态分裂，却不等于持久化、恢复和副作用问题都已经解决。

### 假设改变时，原先的便利也可能成为阻力

![架构不是永久答案，需求和环境会改变其成立的条件](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=12&rect=0,0,960,540&width=960)

前面四个例子体现了抽象泄漏：被隐藏的细节重新影响上层决策。架构成为阻力，不一定是原设计错误，也可能是它固定下来的前提已不合适。Slides 用工厂电气化作类比：把蒸汽动力换成电力，却仍围绕原来的传动轴布局，未必能充分利用独立电机带来的新组织方式。改变技术与改变围绕技术形成的流程，是两件事。

![AI 降低实现与试错成本后，瓶颈可能移向需求、验收、信任和执行](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=13&rect=0,0,960,540&width=960)

对应到软件开发，若实现成本下降，原先不值得做的小需求可能变得值得满足，需求本身也会更快变化。继续把所有变更塞进旧的等待与审批流程，可能只把瓶颈挪到别处。讲义由此推演产业与组织的变化，但单个任务的提效不等于整个产业已完成重组，潜在收益也不意味着人人会自动同等受益。

### MapReduce → Spark / Flink：变化的是问题结构

MapReduce 要求把计算组织成 `map → 按 key 分组 → reduce`。统计访问量时，每条日志输出 `(URL, 1)`，再按 URL 求和。接受计算形式，框架便能组织切分、调度、并行与失败重试。

![MapReduce 把调度和恢复交给框架，但应用仍要满足重算条件](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=18&rect=0,0,960,540&width=960)

限制仍然存在：热门 key 可能集中到一个归约环节；map 若顺手发邮件，重试就可能多发。框架能重新调度任务，不能替任意副作用创造幂等性。

当需求变成反复迭代同一批数据，多轮作业间交换中间结果可能成为负担。Spark 用更一般的计算依赖图和数据缓存提供另一种组织方式；丢失分区可以沿依赖重算，但缓存、分区和内存管理又成为新取舍。

若需求变成持续显示最近五分钟的访问量，就要处理不断到达、乱序和迟到的数据。Flink 的常驻算子、事件时间、水位线与状态检查点共同定义结果语义。恢复不只是重启函数，还要协调输入读取位置与算子状态。

![从迭代到持续流处理，计算语义和技术栈一起演化](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=19&rect=0,0,960,540&width=960)

这不是“旧技术做不了，新技术万能”的排名，而是每套架构都回答一组特定问题，并要求使用者接受相应的约束。

## Everything Is a Plugin：难点在协同

dsh 将模型适配器、工具、会话日志，乃至默认 Agent Loop 都组织为插件。每个插件可以有私有状态，新增能力优先通过扩展接口接入，避免中心程序不断膨胀。

Cordis 管理服务解析、依赖激活、作用域和卸载：需要的服务由谁提供，何时可用，注册在哪里生效，退出时清理什么。**生命周期管理不等于安全沙箱**；作用域不能直接等同于操作系统级的内存、文件或网络隔离。

![插件化先解决装配与生命周期，再面对业务协同](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=20&rect=0,0,960,540&width=960)

不协同，工具、记忆和界面就只是孤岛；随便协同，插件又会直接依赖彼此内部状态。真正需要稳定的是一个小的共同世界模型：

- **Session**：记录发生过什么，提供状态推导依据。
- **Agent**：接收输入，推动后续执行。
- **slots**：界面预留的装配位置，让插件插入按钮、面板等组件。

![Session、Agent 与 slots 构成插件共享的基本对象](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=21&rect=0,0,960,540&width=960)

slots 不强迫所有产品使用同一套界面，私有状态也不等于可以任意保存另一份事实。共享对象负责共同语义，插件内部保留局部实现，才可能把变化限制在边界内。

> [!NOTE] 接口的适用范围
> 以下名称与语义是课程讲解时的 dsh 接口快照，用于理解架构，不表示本文实际运行过代码，也不保证其他版本具有完全相同的接口。

## Session：记录事实，再生成不同投影

### Session = list[Event]

Session 可以理解为有序事件序列，不仅包含聊天，还能容纳工具结果、执行边界和插件业务事实。模型消息、任务状态和界面不是互不相关的三套记录，而是同一历史的不同投影。

投影回答“这些事实在这个用途下意味着什么”。工具执行完成后，界面可以显示结果卡片，业务插件可以计算步骤状态，下一次模型请求可以获得结果。它们共享事实依据，不必靠界面回调顺手同步其他模块。

![Session 接口把记录事实与解释事实分开](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=22&rect=0,0,960,540&width=960)

```js
// 记录与观察事实
session.append(type, data)
ctx.on('session/event', (session, event) => { /* 观察事件 */ })

// 从事实获得不同用途的表示
session.deriveMessages()
ctx.sessionProjections.register(definition)
ctx.sessionProjections.stateOf(session, key)
```

`append` 追加插件负责的业务事件，`session/event` 观察已进入会话历史的事实；`deriveMessages` 生成模型消息历史，`register` 注册业务投影，`stateOf` 读取对应状态。**进入历史不等于已写入磁盘**，持久化保证仍取决于相应机制，不能据此直接宣称崩溃后必然可恢复。

### 可追溯不等于自动正确

如果模型看见一段上下文，应能找到它进入请求的依据；界面显示任务完成，也应能追问对应事实。投影让诊断有起点，却不保证投影规则正确。纠错需要追加补充或更正记录，而不是悄悄改写历史。

要重现历史，还需要对应的事件格式、规则版本和外部输入。重新推导任务状态，也不能重新执行工具副作用。Session 保存事实的价值，必须与正确解释、可靠持久化和外部恢复共同成立。

## Agent：三种输入，三种执行意图

“给模型一段话”过于含糊：是启动新任务，补充资料，还是调整正在做的事情？课程将它们拆成不同接口。

| 接口 | 意图 | 唤醒与进入执行的语义 |
|---|---|---|
| `agent.followup(message)` | 普通后续输入、新一轮任务 | 排入新一轮，并唤醒执行 |
| `agent.inject(message)` | 补充模型上下文 | 等待后续步骤使用，本身不唤醒空闲 Agent |
| `agent.steer(message)` | 中途改变方向 | 尽快进入后续步骤，空闲时也可以唤醒 |

![输入方式与动态上下文决定信息何时进入执行](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=23&rect=0,0,960,540&width=960)

插件拿到一份补充资料，可以 inject，而不必立即开启新工作；用户说“先处理第二份文件”，则更接近 steer。这里的“尽快”仍受执行边界约束：正在运行的模型请求和外部操作不会倒退，已经改过的文件也不会因一句引导自动还原。

### 动态上下文不是启动时的一张快照

画布选区、当前文件、活动任务会随用户操作变化。如果只在插件启动时写入提示词，模型很快就会使用过期状态。动态上下文应在组装时读取当前状态：

```js
// 示意：其余注册字段按课程接口约定提供
ctx.systemPrompt.context({
  /* ... */
  text: () => describeCurrentState()
})
```

这建立了从应用状态到模型上下文的明确通道，但不意味着所有状态都应发送给模型；读取范围、授权和数据外发仍需单独约束。

### session/event 与 agent/pre-step 的时间方向不同

```js
ctx.on('agent/pre-step', async (payload, next) => {
  const decision = await next()
  return decision
})
```

这个处理器先把决策委托给后续链，再原样返回。插件可以按接口约定检查或调整待执行决策；`next()` 不是装饰，不调用它可能短路后续处理链。

![事实监听和待执行决策必须分开，next 决定处理链是否继续](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=24&rect=0,0,960,540&width=960)

`session/event` 面向过去：观察已发生事实，纠正时留下新记录。`agent/pre-step` 面向未来：参与下一步如何执行的决定。把两者混淆，插件改变未来行为就容易变成改写过去，执行和审计也失去共同依据。

## 插件组合：解耦不等于没有冲突

插件通过事件、输入、上下文、Hook、工具和 UI 接口挂在共同总线上。Cordis 可以撤销已注册监听等 effects，但卸载并不会自动撤回插件之前发出的邮件或修改过的文件。

![业务插件经输入、上下文、Hook 和事件接入总线，模型消息与 UI 分别来自投影](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=25&rect=0,0,960,540&width=960)

沿图读一轮工作：业务插件提交输入或贡献上下文，Agent/Loop 推动执行并调用 LLM/Tools 插件，执行事实进入 Session。Session 一路通过 `deriveMessages()` 生成模型所见，一路经业务投影计算状态，再交给 UI slots 装配界面。业务插件观察已提交事实、追加自己的事件，而不必直接知道模型适配器和界面的内部实现。

图底部的 Cordis 负责服务解析、依赖激活、作用域与 effects 卸载；它解决“怎样装上和卸下”，并不自动解决“多个插件对同一事实应当怎样解释”。因此，总线减少直接依赖，却仍然需要明确的语义契约。

更重要的是，装配成功不代表语义兼容。A 改写输入、B 检查输入，先检查后改写与先改写后检查并不等价；两个合法 Hook 也可能分别要求继续和停止。插件还可能依赖另一个插件产生的事件、注册顺序或副作用，形成没有声明的隐藏依赖。

![顺序、冲突与隐藏依赖是插件生态必须面对的成本](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=27&rect=0,0,960,540&width=960)

课堂用十个压缩插件作思想实验：假设每个依次把同一上下文压成一半，最终长度是 `(1/2)^10 = 1/1024`。这是解释组合风险的假设计算，不是实际压缩效果测试，更不意味着信息价值会严格同比缩小。

因此，共同规则还要回答：谁拥有某类事件，什么行为允许共存，冲突如何裁决，顺序是否属于契约，卸载留下哪些状态？插件化不是取消这些问题，而是把问题集中到可以讨论和检查的接口上。

## 生态：复用能力，也把试错留在使用现场

TUI 可以不使用图形 slots，直接调用 Session、Agent API；pdf-reader 声明依赖 `tools` 服务并注册阅读工具；dsh-better-sidebar 则把 Session 重新组织成类似 VS Code 的工作界面。同一套核心对象，可以支撑不同产品外形。

![同一套 Session 和 Agent 能支撑不同界面及工具插件](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=26&rect=0,0,960,540&width=960)

Creator Mode 把这个方向推进一步：用户表达局部需求，Agent 编写、装配乃至热插拔插件，用户立即体验并修改。反馈不再全部经过“转述需求—排期—交付”，而是在使用现场发生。

![生态价值不只在成品数量，也在用户能否直接满足局部需求](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=28&rect=0,0,960,540&width=960)

讲者对社区方向的尖锐评价，表达的是“鼓励用户自己改，还是只收集成品插件”的产品观点，不是社区质量的客观测量。生成门槛越低，越需要明确影响对象、验证方法和失败退出方式；快速试错不免除维护与安全责任。

## 方向一：给已有 App 接入 AI

### lock objects + serialize objects + UI

成熟应用已经拥有对象模型和编辑规则。画布有图形，文档有段落，表格有单元格。模型不必重建整个应用，可以通过很小的连接层接入这些能力：

1. **锁定对象**：确定本轮可修改范围，避免人与模型同时改同一对象。
2. **序列化对象**：把内部结构转换为模型和工具可处理的表示。
3. **提供 UI**：让用户选对象、表达意图、查看结果和停止执行。

![复用应用对象与规则，用小的连接层建立 AI 协作](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=29&rect=0,0,960,540&width=960)

讲义中的 Excalidraw 机制是：用户选中图形并提出修改要求，系统锁定选区及绑定文字，把对象 JSON 交给对应 Session，画布其他部分仍可编辑。模型通过 `replace_selection` 提出替换；工具检查范围，禁止修改选区外对象，通过后先暂存结果，而不是立即写回画布。

**本轮成功结束才提交替换；停止、超时或失败则解锁并保留原选区。** 每张画布对应一个会话，支持继续讨论、切换与恢复。这不是笼统地要求模型“小心修改”，而是应用规则、暂存与提交边界共同控制修改范围。

应用负责对象含义和编辑规则，Harness 负责会话与执行协作。讲者由此提出对独立办公助手形态的挑衅性评价，应理解为产品方向判断，不能推成所有独立助手都没有价值。

## 方向二：GenUI，让界面进入对话

GenUI 不只是模型输出一张 HTML 页面，而是允许生成 HTML + JavaScript 卡片，并建立卡片与 Session、模型上下文之间的双向通道。模型可以生成交互入口，卡片也能把用户操作和当前状态送回会话。

![交互卡片与模型双向连接，让点击和自然语言共同表达任务](../../../files/slides/GSE/DeepSeek%20Harness（1）-slides.pdf#page=30&rect=0,0,960,540&width=960)

下棋的逻辑链是：点击落子，棋局进入上下文，模型选择应手，卡片更新棋盘。用户不必反复输入坐标，也不必在文字回答中重建局面。图表、任务卡和参数面板同样可以让点击精确表达动作，自然语言表达目的。

但职责不能混淆：界面负责展示和输入，规则程序维护回合与合法动作，模型负责选择和解释。**能生成棋盘不等于具有可靠棋力，建立双向通道也不等于每一步都合法。** 本文没有把关键帧未验证的棋盘交互写成视频实测结果。

> [!SUMMARY] 核心结论
> 150 行 Agent 展示的是能力核心，可靠产品还要承担恢复、权限、交付和持续交互。架构通过限制表达方式换取一类便利，但每项便利都依赖有有效期的假设。dsh 用插件组织能力，以 Session 保存事实，以投影生成不同视图，以 Agent 输入与 Hook 明确执行意图和决策边界。插件生态的价值在于让变化有地方发生；代价则是组合语义仍要管理。无论是已有 App 的 AI 增强，还是 GenUI，最终都应把模型的灵活性放进明确、可验证的对象与执行规则中。
