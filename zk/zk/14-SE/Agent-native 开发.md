# Agent-native 开发

前两讲讨论需求和架构，关心的是怎样把意图说清楚、把问题分解好。等到原型开始运行，许多纸面上没有答案的问题才会露出来：规格漏了什么，选定的架构能否承受真实负载，程序究竟做对了没有。

把实现交给 Agent，这些问题依然要有人处理。它可能很快写出一个能运行的版本，却在下一轮忘掉约定，改坏已有功能，或者花很长时间修饰一段根本不该存在的代码。要让它持续参与开发，就得为它准备能接手的工作区、能执行的规则，以及足够具体的反馈。

## 先让原型跑起来

设计到某个阶段，就应该做出原型，让它碰一碰真实问题。“Let it fail” 说的是允许尚未完善的方案接受检验，观察失败发生在哪里，再决定该改什么。

![运行原型让规格背后的隐含假设接受现实检验](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=2&rect=0,0,960,540&width=960)

例如，一个选课系统在单人使用时一切正常，两个人同时争抢最后一个名额，却都选上了。如果规格早已要求不能超额，就要检查容量更新和并发控制；如果规格从未交代竞争时怎样处理，缺口还在需求里。

再往前想一步：即便程序完全符合规格，学生也可能觉得先到先得不公平，更需要候补或抽签。此时继续优化抢课速度，离他们的意图反而更远。原型让这几类问题有机会被区分开，免得把所有不满意都当作代码写错了。

Slides 中莱特兄弟的例子也很贴切。他们发现滑翔机的升力远低于预测，随后自建风洞，重新测量翼型数据。要修正的已经不只是制造过程，还包括设计时相信的那些数据。软件里的负载、用户行为和业务规则，同样需要接受这样的检验。

## Ralph Loop：进展留在工作区里

能读写文件、运行命令的 Agent，比一次性问答多了一种能力：它可以动手改变任务所处的环境，再根据结果继续工作。不过，能做事和知道怎样把事做好，仍然有距离。哪些代码值得抽象，哪些细节不必加固，什么时候应该停下来重新想一想，都还很容易判断失误。

![Agent 越来越自主，但模型尚未稳定掌握所有工程判断](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=3&rect=0,0,960,540&width=960)

Geoffrey Huntley 的 Ralph Loop 把持续开发压缩成了一个很短的循环：

```bash
while true; do
    cat PROMPT.md | claude -p
done
```

每轮重新开始一次对话，仍然读取同一个 `PROMPT.md`。乍看之下，这似乎只是在重复发问。但上一轮改过的代码、写下的日志、留下的任务记录都还在。提示词没有变化，工作区已经变了，下一轮面对的自然也就不是原来的问题。

![Ralph 的推进来自变化的工作区，而非不断改写同一个提示词](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=5&rect=0,0,960,540&width=960)

这个循环没有替开发者回答何时完成、何时放弃。`while true` 只负责再跑一次。若几轮都撞上相同错误，就该检查原因：缺少权限、测试含糊，还是任务本身走错了方向？继续之前，需要有验收条件、重试预算和升级处理的办法，否则它很可能只是把同一个失败做得更贵。

### 下一轮怎样接手

用状态机来描述，就是 “Workspace = State，Agent = Transition”：工作区保存当前状态，Agent 的一轮工作改变状态。代码只是其中一部分，需求、设计决定、测试和运行记录也都属于它。

![需求、实现、测试与运行记录共同组成可继续推进的状态](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=6&rect=0,0,960,540&width=960)

一次修改可能让任务从“尚未实现”变成“已有实现但测试失败”，下一轮再定位原因、修复并验证。任务可以持续很久，超过任何一次会话的长度；前提是每轮结束后留下的材料，足以让后来者接着做。

还是以选课为例。“选课功能已完成”几乎没有交接价值。如果记录写成“普通选课测试通过；两个请求竞争最后一个名额时会超额；复现命令和日志已保存；下一步检查容量更新是否原子化”，接手者就知道哪些结论可信、怎样复现，以及从哪里继续。没有写进工作区的判断，下一轮未必还能找回来。

版本管理又让状态可以分叉，多个 Agent 因而能够分别工作。不过，Git 或 Jujutsu 不会自动替它们拆好任务。几个人同时改同一个接口，仍然会互相覆盖；分支各自通过测试，合起来也可能出错。并行之前，要先分清各自负责什么、依赖什么，合并之后再检查组合结果。

## 给每次改动设一道检查

如果 Agent 的工作是一连串状态变化，那就需要在变化之后检查结果。否则，它只要一轮改坏了关键约定，后面的工作就可能沿着错误继续累积。

![每轮验证将开发循环连接到明确的质量条件](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=7&rect=0,0,960,540&width=960)

这里采用的出发点是“开发者不可信”。人也会觉得只改了一点，不至于出问题；Agent 做得快，也会更快地把这种疏忽带进仓库。与其依赖修改者的自述，不如直接检查程序能否构建、已有功能有没有回归、项目约定是否仍然成立。

把这些检查放进每次集成，再把通过检查的改动送入发布流程，就回到了 CI/CD。

![持续集成减少集成风险，两个 CD 区分可发布与自动发布](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=8&rect=0,0,960,540&width=960)

CI 关心持续集成，两个 CD 的区别则在于是否自动上线：

| 名称 | 承诺 |
|---|---|
| Continuous Integration，持续集成 | 频繁向主干集成小规模改动，每次自动构建和验证 |
| Continuous Delivery，持续交付 | 软件保持可发布状态，上线时机可以由人决定 |
| Continuous Deployment，持续部署 | 通过检查的变更自动上线 |

CI 尤其依赖“小步”和“频繁”。两个人各做一个月，最后合起来跑一遍测试，即使测试是自动的，也没有解决集成地狱。改动范围小、反馈来得早，出了问题才容易找到是哪次变化引起的。

### 检查放在哪里，决定它能否拦住错误

Hook 提供事件触发的机制：提交、推送、PR 更新或主干变化时，执行相应动作。这样就不用等 Agent 想起“还该跑一下测试”。

![本地提醒与远程强制门禁承担不同职责](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=9&rect=0,0,960,540&width=960)

但本地 `pre-commit` 可以被 `--no-verify` 跳过，远程检查也可能只显示失败，照样允许合并。要让规则生效，需要 required checks 与分支保护配合，并且管住直接推送和绕过检查的权限。

合并前检查的对象也要准确。两个 PR 各自通过，不意味着它们叠在一起仍然正确。主干变化频繁时，要验证候选改动与最新主干的组合，必要时借助 merge queue 管理待合并顺序。

## 发布规则要写到能验收

Hook 的机制不复杂，麻烦的是围绕它的业务规则。测试偶尔失败，允许重跑几次？生产故障需要紧急修复，谁有权放行？新版本先部署成功，旧任务随后才完成，会不会把它盖回去？

![Hook 机制简单，合并组合、偶发失败、紧急放行和部署并发才是业务规则](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=10&rect=0,0,960,540&width=960)

这些问题不会因为 Agent 会写 YAML 就消失。配置文件需要实现的，正是团队对这些情况作出的决定。只说“配一套 CI/CD”，留给实现者猜测的空间仍然太大。

以课程网站为例，一份能够落实的 Spec 至少要交代：

1. PR 新增提交后重新运行 Lint 和测试，合并前验证与最新主干的组合。
2. 必需检查失败时禁止合并，例外放行需要明确权限和记录。
3. `main` 更新后，对这次提交运行检查并构建页面。
4. 检查与构建全部通过，才部署这次构建的产物；失败时保留上一版。
5. 发布重叠时，过时产物不得覆盖新版本。

![合并条件、发布对象与失败行为都需要进入规格](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=11&rect=0,0,960,540&width=960)

其中“这次提交”和“这次构建的产物”值得说清。测试了一份代码，发布时却取到另一份内容，前面的绿灯就失去了意义。Lint、测试和构建也各管一部分问题：格式符合约定、程序行为符合预期、产物能够生成，需要分别验证。

验收这套流程时，还得主动制造一次 Lint 错误、一次测试失败，看它是不是真的不让合并、不让发布，旧版是否仍然可用。修复之后，再确认正常路径恢复。如果失败状态一路传下来，最后仍部署了出去，首先该查的是流程怎样处理失败，而不是急着再补几条测试。

## CI 挡住问题，Agent 接着修

Agent 参与开发后，一些原本需要人反复提醒的习惯，值得变成自动检查。比如入口文档越写越长，同一条规则在几处重复维护，为一个不重要的边界情况添了很多代码。单看每次修改，似乎都有理由，累积起来却很难维护。

![质量要求需要进入生产过程，不能只靠实现者自行承诺](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=12&rect=0,0,960,540&width=960)

提示词里写一句“保持简洁”，很难保证后续每轮都遵守。能明确判断的部分，可以交给程序：限制入口文档的规模，检查禁止的依赖方向，运行格式化和静态检查。触发规则后，让 Agent 根据报错修正，再按相同标准验证。

![把 Agent 的常见偏离分别转化为自动检查与人工判断](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=13&rect=0,0,960,540&width=960)

但文档短，不代表信息组织得好；复杂度指标低，也不代表抽象合理。程序适合指出“越过了哪条线”，判断这条线是否合适，仍然需要人。报错信息最好带上位置、规则理由和修复方向，免得下一轮只知道红灯亮了，却不知道该查哪里。

测试和检查规则本身还要受到保护。负责实现的 Agent 如果能随手删掉断言，就能用很小的代价换来全绿。规则当然可以修改，但应当有需求依据和单独的审查。修正过时的测试，与为了过关而放宽测试，不能混为一谈。

## Harness：让 Agent 自己找到依据、看到结果

开发者长期记在脑中的许多东西，并没有写在代码里：某个接口为什么保持这个形状，哪种重试不能做，过去为什么放弃了一个方案。人协作时可以临时问一句，Agent 换一轮会话后却未必知道该问谁。

课堂引用的 OpenAI Harness engineering 实践，从一个空仓库开始，把不少工程工作放到了环境建设上。

![工程知识外部化，并让每份工作区拥有直接观察程序的能力](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=14&rect=0,0,960,540&width=960)

设计、计划和决策进入版本管理，`AGENTS.md` 负责指路，详细内容按需查阅。入口不必塞进所有规则，但应当让 Agent 找得到相关材料，也看得到规则背后的理由。否则，同一句约定换一个场景，仍然容易被误用。

运行环境也要能让它独立观察问题。用户说“按钮没反应”，可能是请求没发出去、服务端报错，也可能是结果到了却没更新页面。让 Agent 自己启动应用、操作页面、查看请求和日志，比反复转述现象更容易找到原因。

![可检查的架构规则与持续清理共同约束生成过程](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=15&rect=0,0,960,540&width=960)

依赖方向、日志字段、错误传播等约定，可以逐步落实为 Lint 或结构测试。偏离规则的代码则做小规模、持续性的清理，避免后来生成的代码继续照着坏例子写。

课上那句“ClosedAI”的吐槽也需要放回具体语境：文章谈了这些实践，却没有附上该内部项目可直接复用的完整 CI 门控配置。它说的是公开材料不够用，不是 OpenAI 没有 CI。读完一篇经验文章，离在自己的仓库里做成这套环境，还有不少细活。

## 三种不同的工程做法

### Stripe：固定工序直接用程序执行

课堂引用的 Stripe Minions Blueprint，把需要判断的步骤和已经确定的工序放在同一条工作流里。理解任务、实现和修复交给 Agent；运行 Linter、推送分支等步骤由普通代码执行。

![混合工作流把确定步骤固化，只在需要判断的位置调用 Agent](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=16&rect=0,0,960,540&width=960)

它对完整 CI 的重试也设了上限：先在本地处理 Lint，再推送并运行 CI；有必要时让 Agent 修一次，第二轮之后交回人类审查。这是该团队对成本和收益的取舍，不宜直接当作所有项目的最佳次数。

把每次都必须做、做法又确定的工序写进流程，模型就不必反复决定是否运行检查、是否推送分支。需要理解任务和处理异常时，再让它作判断。

### Anthropic：先让失败能够被拆开

在课上介绍的 C 编译器实验中，16 个 Agent 一起编译 Linux，却撞上同一个错误，重复修复，甚至覆盖彼此的改动。多开进程并没有带来更多独立的进展。

![借助 GCC 参照与文件子集，把单一失败拆成可分别验证的问题](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=17&rect=0,0,960,540&width=960)

后来，大部分文件改用 GCC，只把不同子集交给新编译器。遇到失败，再把部分文件换回 GCC，逐渐缩小有问题的集合。这样，不同 Agent 才有机会面对不同的失败入口，分别定位和修复。

文件单独通过以后，组合仍然要检查。但在增加 Agent 数量之前，先改变验证方式，已经让任务更容易分开。这也说明，测试怎样组织，会直接影响开发工作怎样组织。

### StrongDM：把验收和练习环境一起造出来

按课堂引用的 StrongDM 自述，Agent 可能用极简实现应付狭窄测试，甚至修改测试来迁就代码。他们把端到端用户故事组织成 scenarios，常放在代码库之外，留出一份相对独立的验收依据。对于含 Agent 的软件，还要观察多条执行轨迹满足用户意图的情况，而不能只挑一次成功运行。

![独立场景与服务行为替身扩大了可反复练习的失败空间](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=18&rect=0,0,960,540&width=960)

Digital Twin Universe 则给外部服务制作行为替身，模拟 API、边界条件和故障。迁移到选课系统，就是把“最后一个名额被别人抢走”“提交已经成功，响应却丢失了”这类情况做成能够反复运行的场景。

这样的环境可以提高练习频率，但需要先与真实服务对照。若替身漏掉关键约束，Agent 只会越来越擅长通过这个简化考场。验收放在仓库外，也只是增加独立性，场景覆盖了什么仍然要认真检查。

## 什么时候该改架构

持续清理技术债，有点像 garbage collection：处理重复、修正文档、整理接口，让坏模式不再扩散。可有些系统越清理越整齐，问题还是解决不了，因为失效的是设计的前提。

![真实负载和异常暴露设计假设，持续清理不能代替及时重构](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=20&rect=0,0,960,540&width=960)

一个写入节点配多个完整读副本，早期可以分担读压力。但每个副本仍然要处理全部更新。写入不断增长时，继续增加读副本，未必能解除复制和 I/O 的瓶颈。这种情况下，整理命名、去掉重复代码，都没有改变系统承担负载的方式。

Friendster 的案例把这个问题讲得更具体。按课程引用的工程师复盘，完整副本都要重放写入，随后出现 I/O 压力和复制延迟。工程师提出按用户分片，却没能在当时的组织环境中推进，相关设计后来在 Flickr 落地。

![及时重构既要求技术上看得清，也要求组织上改得动](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=21&rect=0,0,960,540&width=960)

看出容量瓶颈，并不代表迁移就会发生。数据怎么搬，职责怎么分，谁承担上线风险，都要有人协调。这份复盘能帮助理解技术判断与组织执行之间的距离，但不能据此把一家公司的兴衰归结为一个数据库方案。

Webvan 和 Quibi 又把问题往业务前提上推了一步。按课堂引用的材料，Webvan 在 2000 年报中披露配送中心业务量不足设计容量的 40%；仓配能力已经建起来，订单规模却没有跟上。Quibi 关停时，管理层则谈到了独立流媒体服务的需求假设与推出时机。

![Webvan 与 Quibi 将失败分析从实现问题推进到业务前提](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=22&rect=0,0,960,540&width=960)

年报、工程师复盘和管理层解释的证据分量不同，也不能拼成一个通用的失败公式。不过，把它们放在一起，确实能帮助分清几种处境：有时要改实现，有时要改架构，还有时得重新考虑这件事值不值得做。

Agent 让补功能、添页面和写文档更便宜了，也就更容易让项目在这些地方不断膨胀。外观看起来越来越完整，最初的假设却可能一直没被验证。只要判断错了修正的层次，更多实现也只是在延续原来的问题。

## 判断力需要尝试的机会

不少工程判断很难只靠读懂术语获得。没有处理过并发失败，就不容易看见事务边界；没有经历过一次漫长的集成，也很难体会小步提交的价值。前面那些做法，往往是在具体系统里试过、失败过，才逐渐变得清楚。

![实践资源、学习动机与学习能力共同影响经验的积累](../../../files/slides/GSE/Agent-native%20开发-slides.pdf#page=23&rect=0,0,960,540&width=960)

这也是课程最后担忧实践机会差距的原因。Token 预算会影响一个人能做多少次尝试，但花费本身不会自动变成经验。还需要读懂失败、比较方案，记下这次为什么有效，再用下一轮运行检验判断。

“实践机会的差距会积累成判断力的差距”，在这里是一种教育上的担忧，而不是已经确定的社会结论。对学习者来说，有价值的练习应当允许自己把系统跑起来，看见它在什么条件下出错，再亲手完成一次有依据的修改。

> [!SUMMARY] 核心结论
> Agent-native 开发需要为 Agent 留下可接手的工作状态，并用检查、运行环境和验收结果指导后续修改。规则能挡住一部分已知错误；当需求或架构的前提失效时，仍然要停下来重新判断该改什么。
