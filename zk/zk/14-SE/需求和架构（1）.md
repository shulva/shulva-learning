当目标已经明确时，Agent 可以快速生成实现、测试、断言，甚至形式化证明。代码生产变便宜以后，真正决定软件质量和寿命的，越来越是前面的两个问题：**我们究竟要做什么，以及怎样组织系统才能承受下一次变化。**
## 代码便宜以后，什么变得更重要

“软件不软”并不是说代码不能修改，而是说修改很少只影响一个地方。软件中充满隐含依赖，一处需求误解可能沿着设计、实现、测试和历史数据传播，最后变成大范围返工。

![需求对齐、方案选择和实现返工共同说明软件并不柔软](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=2&rect=0,0,960,540)

传统软件工程为需求访谈、建模、模块划分和开发流程创造了许多方法。但需求、产品和架构又很难像算法性能一样做受控实验。

不同参与者可能连“问题是什么”和“怎样算成功”都没有共识，这类问题被 Rittel 和 Webber 称为 [Wicked Problems](https://doi.org/10.1007/BF01405730)，即难以独立定义、也没有唯一正确答案的棘手问题。

![需求与架构难以研究，是因为参与者可能连成功标准都不一致](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=3&rect=0,0,960,540)
Agent 改变了成本结构。目标足够明确时，生成代码和并行实现已经非常便宜。因此，需求、产品设计和架构成为新的生产力杠杆：

- 好的抽象可以让大量实现、测试和验证工作都变简单
- 含混的决定也会被 Agent 快速复制到整个系统
- 如果只追求生成速度，产物会堆积成难以解释和维护的 AI Slop

![代码生成变便宜后，需求、产品设计和架构成为生产力杠杆](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=4&rect=0,0,960,540)

> [!NOTE] AI 放大的是已有方向
> Agent 可以提高执行速度，却不会自动保证方向正确。边界清楚、反馈可靠时，它会放大生产力。需求含混、架构失控时，它也会更快地放大混乱。

## eg: 教务系统为什么会陷入需求泥潭

教务系统看起来只是课程、成绩和学生信息的增删改查，实际上覆盖了学生从入学到毕业的完整过程：

- 培养方案与学籍管理
- 开课、排课、选课和先修校验
- 考试、成绩、缓考、补考与重修
- 交换课程和课程替代认定
- 学分统计与毕业审核
- 教师、教务员、辅导员、财务和教务处之间的协作

![教务系统从入学到毕业连接了多类业务与参与者](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=7&rect=0,0,960,540)

经典需求工程建议访谈需求方，但把所有学生、教师、教务员、教务处、财务和辅导员都访谈一遍，周期可能已经超过一次课程开发。更困难的是：

- 用户熟悉普通流程，却未必能一次列出所有允许的和禁止的行为
- 不同角色的目标可能冲突
- 业务规则会随着政策和组织变化
- 一些线下决定尚未进入系统

学生希望选上满员的必修课，教师希望控制班额，教务员又要保证学生按时毕业。此时系统面对的不是信息不足，而是必须有人作出价值判断和业务裁决。

![教务需求既难以说清，也可能因参与者目标不同而无法达成一致](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=8&rect=0,0,960,540)
### 培养方案：规则、例外与冲突

假设一位 2024 级学生在 2026 年转入计算机专业，并适用目标专业的 2024 版培养方案：

- 毕业至少需要 160 学分，各类别还要分别达标
- 数学要求可以由不同课程组合满足
- 算法课要求先通过数据结构，缓考学生可以暂选
- 两门交换课程经批准可以合抵一门必修课
- 同一份学分不能再次计入专业选修
- 重修只计一次学分，但成绩单保留历次记录

这些规则单独实现并不困难，困难在于它们会组合。转专业、交换、缓考、课程替代和选课窗口可能同时作用于同一名学生。

![培养方案中的学分、替代、先修和人工豁免会相互作用](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=9&rect=0,0,960,540)

现实中还会出现线下批准的特殊情况。如果系统只能保存一个“视为满足”的布尔值，却不能记录批准人、理由、适用对象和方案版本，工程师最后只能直接修改数据库。临时问题虽然解决了，业务含义却丢失了。

课堂案例中，把某位同学的缺课次数直接改成 `-1` 后，所有能够查询到该选课记录的功能都发生故障。这说明一个看似局部的数据假设，已经被系统中许多功能共同依赖。异常值进入后，问题便沿着依赖扩散。

![绕过系统直接修改数据库，会让隐含的数据假设沿依赖传播](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=10&rect=0,0,960,540)

> [!IMPORTANT] 例外本身也是业务
> 真正的需求不是给管理员留一个万能按钮，而是让系统表达谁批准了什么例外、依据是什么、对谁和哪个规则版本生效，以及这项决定是否可以被撤销或复核。

### MVP 帮助发现需求，也会掩盖困难

AI 让 MVP 前所未有地便宜。先把课表、选课和审核流程做出来，用户很快就能指出“这门课已经在交换时修过了”。产品试用因此成为发现隐含需求的一种手段。

![MVP 通过可操作的产品帮助用户说出此前没有表达的需求](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=11&rect=0,0,960,540)

但正常路径跑通，也容易带来已经“驾驭 AI”的错觉。转专业、课程替代、缓考、历史规则和人工审批等 dark corners，可能还没有出现。

![需求变化会穿透整个软件工程的数据依赖图](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=12&rect=0,0,960,540)

Brooks 在 [No Silver Bullet](https://cgi.csc.liv.ac.uk/~coopes/comp319/2016/papers/NoSilverBullet-Brooks1987.htm) 中区分了软件生产中的偶然困难和本质困难。工具可以降低实现成本，却不能消除需求冲突、概念复杂性、历史包袱和持续变化。MVP 很有价值，但不是能够一次解决所有软件问题的“银弹”。

## 软件架构：为复杂性和变化安排位置

软件架构决定系统怎样分解问题、组织依赖和分配职责。好的架构并不会消灭复杂性，而是让复杂性有明确归处，让变化尽量停留在边界之内。

![架构的作用是驾驭复杂性，并让变化停留在可控边界内](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=14&rect=0,0,960,540)

Parnas 在 [On the Criteria To Be Used in Decomposing Systems into Modules](https://ckrybus.com/static/papers/decomposing_systems_into_modules_1972.pdf) 中提出，不应只按处理步骤划分模块，而应围绕困难或可能变化的设计决策划分，并把这些决定隐藏在稳定接口后面。

### 再小的程序也有架构

真正的问题不是函数数量，而是边界是否成立：

- 数据怎样在阶段之间流动
- 谁拥有和修改状态
- 核心算法是否知道输入输出的具体格式
- 更换输入格式时需要修改几个模块
- 错误由哪个阶段负责解释

如果四个函数随意修改同一组全局变量，它们仍然紧密耦合。函数、类型、作用域和资源所有权之所以重要，是因为它们能把设计意图变成约束。

![函数、类型和作用域等语言机制都可以承载架构边界](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=16&rect=0,0,960,540)

### 十行汉诺塔：同一个问题的多种表示

非递归汉诺塔可以有几种完全不同的写法：

| 表示方式   | 复杂性放在哪里         | 优点与代价                   |
| ------ | --------------- | ----------------------- |
| 数学规律   | 步号、盘号和移动方向之间的关系 | 代码短，但规律需要单独证明，规则改变后可能失效 |
| 任务栈    | 尚未执行的递归子任务      | 保留问题分解，容易从递归算法转换        |
| 抽象机器   | 栈帧、程序计数器、调用和返回  | 能解释一般程序执行语义，但表示更底层      |
| 显式状态或图 | 合法状态与转换关系       | 便于验证规则，也可能带来更大的状态空间     |

![同一个汉诺塔问题可以把复杂性放在数学、任务、机器或状态中](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=22&rect=0,0,960,540)

Zhang 和 Norman 对同构问题的研究表明，表示方式会显著改变人的解题难度，见 [Representations in Distributed Cognitive Tasks](https://pages.ucsd.edu/~scoulson/203/zhang.pdf)。代码写不出来，不一定是缺少某个 `if`，也可能是当前表示让关键规律难以看见。

> [!NOTE] 架构是一种看问题的方式
> 表示不会凭空消除复杂性，而是重新分配复杂性。选择表示方式，就是选择让哪些操作简单、哪些性质容易验证、哪些变化需要付出代价。

## eg: 两千行二维码程序：真正需要的是编译器

课程中的二维码任务要求用 Excel 公式从输入字符串计算二维码。直接生成所有公式，很快会出现两个问题：

- 公式极长，括号、单元格引用和数组运算纠缠在一起
- 改 Excel 版本、二维码位置、计算方式或输入数量，都可能影响整片公式

![直接生成二维码公式会得到脆弱而难以演化的实现](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=24&rect=0,0,960,540)

跳出 Excel 公式后，问题变成：二维码算法容易用普通程序描述，但怎样把这个计算过程可靠地映射到工作表？这更像一个小型编译器问题。

### 用中间表示隔离算法与 Excel

中间表示 IR（Intermediate Representation）可以把二维码计算表达成一张计算图。图中包含输入、常量、异或、查表和条件选择等节点，边表示数据依赖。高级语言负责构造计算图，后端再把图翻译到具体环境。

![二维码生成器的核心问题可以重述为编译器和中间表示](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=25&rect=0,0,960,540)

必须区分两个时间：

- **生成时**：Python 循环根据容量展开有限计算步骤，并构造计算图
- **运行时**：用户修改工作表输入，Excel 根据图生成的公式重新计算

如果生成器提前把当前输入算成固定二维码，它只是硬编码了一次结果。字符串内容决定的条件分支应变成 `Select(cond, a, b)` 一类节点，留到运行时判断。

同一份计算图还可以生成 Python 程序和 Excel 公式。Python 后端适合调试和建立参考结果，Excel 后端负责把符号计算映射到单元格。

![一份中间表示可以生成 Python 与 Excel 两种执行方式](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=26&rect=0,0,960,540)

引入 IR 后，不同变化可以落到不同模块：

| 需求变化          | 主要修改位置    |
| ------------- | --------- |
| 兼容旧版或新版 Excel | 目标能力与公式后端 |
| 移动二维码位置       | 布局和地址解析   |
| 替换一种计算方式      | 算法构造或图优化  |
| 增加输入单元格       | 输入绑定与组合规则 |

![围绕变化划分模块，使需求变化能够找到自己的位置](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=27&rect=0,0,960,540)

### 中间表示必须有明确语义

IR 不是随意拼装的节点集合。至少要明确：

- 字节和整数的取值范围
- 整数除法规则
- 字符串编码
- 数组形状与容量
- 每个节点允许的输入和输出类型
- 节点来源以及错误怎样追踪

构图阶段可以检查类型与容量，后端统一处理括号和引用。这样，算法作者不必在每个公式里重复解决目标语言细节。

![中间表示需要可检查的语义，并保留依赖与来源](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=28&rect=0,0,960,540)

两个后端还能进行差分验证：输入相同数据，比较 Python 和 Excel 实际重算后的中间值与最终结果。但两个后端可能共享同一个算法错误，因此还需要 [Nayuki QR Code Generator](https://github.com/nayuki/QR-Code-generator) 或二维码解码器等独立实现交叉检查。

### 性能优化也要有自己的位置

计算图提供了独立的优化层：

- 与输入无关的节点可以进行常量折叠
- 相同的纯计算可以共享，避免复制巨型公式
- 支持 `LET` 时可以在公式内复用
- 跨公式复用或旧版本 Excel 可以使用辅助单元格
- 是否内联应根据复用次数、计算成本和目标版本限制决定

[Microsoft Excel 计算性能指南](https://learn.microsoft.com/en-us/office/vba/excel/concepts/excel-performance/excel-improving-calculation-performance)同样建议减少重复计算、拆分巨型公式并用测量验证效果。

![先优化计算图，再根据 Excel 的真实成本决定中间结果放在哪里](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=29&rect=0,0,960,540)

## 回到教务系统：当前状态里藏着什么

十行汉诺塔和两千行二维码程序说明了表示方式的重要性。回到几十万行的教务系统，架构仍然是如何观察问题的选择，只是错误的代价和历史负担更大。

### CRUD 的适用范围与局限

CRUD 用当前状态描述世界：系统保存当前有哪些学生、课程和选课记录，每个功能负责查询或修改这些状态。数据库规范化可以减少重复数据和更新异常。对简单信息维护而言，这种架构直接而有效。

![CRUD 把系统理解为当前状态及其查询和修改](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=33&rect=0,0,960,540)

问题在于，许多字段并不是原始事实，而是推算出的结果。一个 `can_graduate = true` 可能来自：

- 课程成绩
- 课程替代审批
- 培养方案版本
- 人工豁免
- 当时适用的业务规则

如果只保存最终布尔值，系统便失去了结论的来源。成绩更正后，团队无法知道哪些学分认定和毕业审核需要重新检查。数据库没有重复字段，并不代表业务依赖得到了保存。

![当前状态可能把历史事实、规则和业务决定压缩成无法解释的结果](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=34&rect=0,0,960,540)

政策更新和领导批准可能已经发生，系统却尚未表达。为了让学生及时毕业，工程师把数据直接改成满足条件。如果只留下结果，几个月后就无法区分它是正常审核、正式特批还是一次误操作。

![系统外已经发生的决定若不能表达，数据会逐渐成为无法解释的黑洞](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=35&rect=0,0,960,540)

### 身份、属性和历史关系

当“计算机系”变成“计算机学院”时，`dept_id` 应继续使用旧值，还是建立新值？

![旧 ID 与新 ID 的选择分别承诺了不同的业务语义](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=37&rect=0,0,960,540)

如果身份延续，可以保留稳定 `org_id`，让名称、层级和隶属关系按有效期保存版本。如果产生了新组织，则建立新 ID，并记录带日期的承继关系。查询还必须说明采用“当时归属”还是“按今天口径汇总”。

系统运行以后，代码仍然可以重写，已经丢失的历史依据却不能凭空补回。同一个“已毕业”可能来自正常审核、人工特批，也可能来自一次救火修改。没有保存的依据，AI 也无法可靠推断当时发生了什么。

![运行中的系统可以重写代码，却无法自动恢复没有记录的历史语义](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=38&rect=0,0,960,540)

## 把依赖与历史变成一等对象

既然业务结论依赖事实、规则和其他决定，就可以把这些依赖变成系统能够明确表示、保存和查询的一等对象，而不是只留在人脑或散乱日志里。

![把依赖变成一等对象，才能解释状态从何而来](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=39&rect=0,0,960,540)

### Event Sourcing：从事件历史生成状态

Event Sourcing（事件溯源）不只保存“张三当前选了生成式软件工程”，还保存“张三的选课申请已被接受”“后来退选”“再次选入”等已经发生的事件。按顺序把事件应用到初始状态，就可以得到当前状态。

账本是直观类比：余额告诉我们现在有多少钱，逐笔收支解释余额为什么成为当前值。详细介绍见 [Martin Fowler: Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)。

![事件溯源保存已接受的事件，并通过投影和重放生成状态](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=40&rect=0,0,960,540)

事件溯源包含几个重要概念：

- **事件**：系统已经接受的事实，例如选课已接受、成绩已登记
- **投影**：把事件转换成课表、点名册或审核视图
- **重放**：重新应用历史事件，恢复或重建投影
- **快照**：从已知历史位置保存状态，避免每次从头计算

事件历史只说明发生了什么。要解释一次毕业审核为什么通过，还需保存它使用了哪些输入、哪一版规则和什么审批依据。

### Replay：恢复历史不等于按新规则重算

重放至少有两种目的，不能混为一谈：

1. **恢复历史**：还原当时记录的事实和决定
2. **重新计算**：用今天的规则回答“如果现在审核，会得到什么结果”

一名学生已经获得学位，是已经发生的事实。用新规则重算不通过，不能让授予学位的历史自动消失。如果需要撤销，应经过新的业务流程，并记录新的决定。

![恢复当时历史与按新规则重新计算是两个不同问题](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=41&rect=0,0,960,540)

### CQRS：怎样作出决定，怎样查看结果

CQRS（Command Query Responsibility Segregation，命令查询职责分离）把写模型和读模型分开：

- Command 表达业务意图，例如“申请选课”。写模型检查资格、容量和冲突，然后接受或拒绝
- Query 服务不同使用者，例如学生课表、教师点名册和教务统计

读写模型可以位于同一进程和同一数据库。CQRS 关注职责分离，是否采用事件溯源是另一个选择。

![CQRS 分别设计怎样作出业务决定和怎样展示查询结果](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=42&rect=0,0,960,540)

如果读模型异步更新，就会出现“选课已经确认，课表还没刷新”的短暂间隙。界面必须能够解释这个状态，系统也要明确“选课成功”由哪个环节确认。只剩最后一个名额时，两位学生不能同时占位成功，容量检查和占位仍需处于同一一致性边界内。

### DDD：让业务概念决定软件边界

DDD（Domain-Driven Design，领域驱动设计）要求开发者和业务人员共同建立领域模型，让“选课”“学分认定”“毕业审批”成为软件中的明确概念。

在一个边界内，同一个词应具有一致含义，这叫统一语言。庞大系统却不需要所有业务共享一份万能模型。限界上下文（Bounded Context）明确模型适用的范围，再定义不同上下文怎样协作。

![DDD 用统一语言和限界上下文让业务概念决定软件边界](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=43&rect=0,0,960,540)
“学生”在不同上下文中具有不同模型：

- 选课关心资格、时间冲突和名额
- 财务关心应收与到账
- 毕业审核关心学分认定和适用方案

“课程成绩已通过”可以成为学分认定的输入，但能否计入专业毕业学分，应由学分认定上下文决定。如果把二者都压缩成 `passed` 字段，系统将无法表达“通过课程却不满足毕业要求”。更多概念见 [DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)。

## 架构选择没有统一答案

CRUD、CQRS、Event Sourcing 和 DDD 并不是由简单到高级的升级路线，而是在不同约束下作出的选择。

| 方案 | 适合解决的问题 | 需要承担的成本 |
|---|---|---|
| CRUD | 简单信息维护，以当前状态为中心 | 历史依据和推导关系容易丢失 |
| CQRS | 写入约束和查询形态明显不同 | 读写同步、短暂不一致和重复提交处理 |
| Event Sourcing | 需要追溯变化、解释历史或重建状态 | 事件版本、重放、副作用隔离和并发控制 |
| DDD | 业务概念复杂，不同范围对同一词理解不同 | 需要持续维护统一语言、边界和上下文关系 |

![几个架构关键词会把同一个业务系统带向不同方向](../../../files/slides/GSE/需求和架构（1）-slides.pdf#page=47&rect=0,0,960,540)

判断一种架构是否值得采用，可以持续追问：

- 它把哪种复杂性放到了哪里？
- 它让哪一种变化更容易？
- 哪些不变量必须一起保持正确？
- 哪些历史和依赖必须留下来？
- 新增的结构带来了什么维护责任？

> [!SUMMARY] 核心结论
> 代码越容易生成，越需要把注意力放在少量但影响深远的决定上。架构不是技术名词的堆叠，而是选择怎样表示业务、保存哪些事实、让谁维护约束，以及变化沿什么边界传播。
