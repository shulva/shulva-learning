可以先把一个软件工程项目理解为一个目录。目录中混合着需求、接口、测试、源码、配置与构建脚本，这些内容经过构建或运行，最终形成可交付的软件。但如果只保存目录当前的样子，就无法回答下面这些问题：


![软件工程项目是目录、文件与可交付物](files/slides/版本管理（1）-slides.pdf#page=5&rect=0,0,960,540)

- 昨天能运行，今天改坏了，怎样恢复？
- 一个功能只完成了一半，怎样暂时放下并修复另一个问题？
- 多个人或多个 Agent 从同一个版本出发，怎样汇合各自的修改？
- 怎样知道某段代码为什么出现，又如何验证它仍然正确？

最朴素的办法，是复制出“项目-v1”“项目-v2”“项目-最终版”等目录。这种做法能够保留旧文件，却把版本之间的来路、文件之间的配套关系和多人协作过程都交给人脑记忆。RCS、CVS、SVN 和 Git 逐步把这些工作交给了版本管理系统。Git 因 Linux 内核的大规模协作需求而诞生，具体历史见 [Git 简史](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git)。

![版本管理从复制目录发展到保存项目历史与协作关系](files/slides/版本管理（1）-slides.pdf#page=11&rect=0,0,960,540)


> [!NOTE] 项目由原子变更推动
> Git 保存项目的一个个快照，提交则记录快照之间的关系。好的工程历史不是文件的随意堆积，而是一系列围绕明确意图组织，并且可以解释、验证和撤销的原子变更。

![项目由原子变更推进](files/slides/版本管理（1）-slides.pdf#page=30&rect=0,0,960,540)

## 如何学习软件工程工具

会背命令不等于真正使用过 Git。更重要的是在操作前能够预测结果，在操作后能够观察并解释变化。例如，发生文本合并冲突时，冲突双方的内容以及 `<<<<<<<`、`=======`、`>>>>>>>` 等标记，通常会直接写入工作区文件，`git status` 则会报告未合并状态。完整过程见 [Git 分支与合并](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging)。

公开仓库本身也是高密度的学习材料。浏览时可以把注意力落到一个具体问题上，例如“这个项目中有什么细节是我自己实现时不会想到的”，再沿着代码、历史和讨论寻找答案。

![Virtually Implement：先在脑中做一遍](files/slides/版本管理（1）-slides.pdf#page=9&rect=0,0,960,540)

这种方法把阅读变成主动比较。相关研究将“把步骤与原理联系起来”的过程称为自我解释，见 [Chi 等人的研究](https://onlinelibrary.wiley.com/doi/abs/10.1207/s15516709cog1302_1)。专家知识也不是零散事实的集合，而是围绕核心概念组织起来的网络，见 [How People Learn](https://www.nationalacademies.org/read/9853/chapter/5)。

学习 Git 时可以不断追问：

- 命令执行后，工作区、暂存区和历史分别发生了什么？
- 哪个引用移动了，产生了什么新的父子关系？
- 这个文件是项目的输入，还是构建或运行产生的结果？
- 这次修改能否独立理解、验证和撤销？

还可以使用 [Learn Git Branching](https://learngitbranching.js.org/) 等工具观察提交图。可视化本身不是目的，关键仍是先预测、再操作、再解释。

## Git 的核心模型

Git 管理的是**项目快照**。快照描述了被纳入版本管理的文件在某个时刻的内容和目录位置。之所以要以项目为单位保存，是因为源码、接口、测试和配置往往必须配套变化。只恢复旧代码却保留新配置，可能拼出一个在历史上从未正确运行过的组合。

一次提交（commit）把快照与作者、说明、父提交等信息联系起来。父提交记录了新状态从何而来，多个提交也由此连接成历史。删除一个已经提交过的文件并再次提交，只表示新快照不再包含它，旧快照中仍然保留着原文件。Git 在逻辑上提供完整快照，在存储上则通过 blob、tree 和 commit 等对象复用未变化的数据，见 [Git 的数据模型](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)。

![Git 管理项目快照](files/slides/版本管理（1）-slides.pdf#page=13&rect=0,0,960,540)

![从恢复、配套修改与多人协作的需求中推导出项目快照](files/slides/版本管理（1）-slides.pdf#page=14&rect=0,0,960,540)

### 工作区、暂存区与提交历史

| 层次 | 保存的内容 | 常用观察方式 |
|---|---|---|
| 工作区 | 当前正在编辑的文件 | `git status`、`git diff` |
| 暂存区，也叫 Index | 下一次提交准备采用的内容 | `git diff --cached` |
| 提交历史 | 已经记录的项目快照及其关系 | `git log`、`git show` |

执行 `git add hello.c` 时，放入暂存区的是那一刻的 `hello.c`。如果 add 后再次修改文件，普通的 `git commit` 仍会提交暂存区中的旧内容，后续修改则继续留在工作区。暂存区的价值在于组织下一次提交，而不是把当前所有修改被动地捆在一起，见 [`git add` 文档](https://git-scm.com/docs/git-add)。

![从空仓库到暂存区与提交](files/slides/版本管理（1）-slides.pdf#page=15&rect=0,0,960,540)

几个基础操作可以放回这个模型中理解：

- `git init` 在当前目录建立仓库。
- `git clone` 从已有仓库建立本地副本。
- `git add` 把选定内容放入暂存区。
- `git commit` 根据暂存区创建新快照，并推进当前分支。
- `git diff` 比较工作区与暂存区，`git diff --cached` 比较暂存区与当前提交。

### 分支、合并与变基

分支名可以理解为指向某个提交的可移动引用。在通常的分支工作方式中，`HEAD` 表示当前所在的分支，新提交会让该分支引用向前移动。

假设 `main` 和 `feature` 都从提交 `B` 出发，后来分别产生了新的提交：

```text
      C---D  main
     /
A---B
     \
      E---F  feature
```

此时，两条分支上的修改可能完全兼容，但它们的历史已经分叉。`merge` 和 `rebase` 都能让 `feature` 的修改与最新的 `main` 汇合，区别在于是否保留这次分叉历史。

#### `git merge`：汇合两条真实发生过的历史

在 `main` 上执行：

```bash
git switch main
git merge feature
```

Git 会寻找共同祖先 `B`，比较 `B → D` 与 `B → F` 两组变化，并生成合并结果。分支已经分叉时，通常会创建一个有两个父提交的 merge commit：

```text
      C---D-------M  main
     /           /
A---B           /
     \         /
      E---F----/     feature
```

`M` 的两个父提交是 `D` 和 `F`。这表示两条开发路线都真实存在，并在 `M` 处汇合。原来的 `C`、`D`、`E`、`F` 都没有被改写，已有提交的 ID 也不会变化。

如果 `main` 自分支创建后没有新提交，`feature` 只是 `main` 的直接后续，Git 默认不需要创建 `M`，只把 `main` 指针向前移动。这叫 **fast-forward merge**。如果希望即使能够快进也保留明确的合并节点，可以使用 `git merge --no-ff feature`。

#### `git rebase`：把本分支的修改重放到新起点

在 `feature` 上执行：

```bash
git switch feature
git rebase main
```

Git 会先找出 `feature` 独有的提交 `E`、`F`，计算它们各自引入的修改，再以 `D` 为新起点依次重放。结果看起来像 `feature` 从最新的 `main` 开始开发：

```text
A---B---C---D  main
             \
              E'---F'  feature
```

这里的 `E'`、`F'` 并不是被搬到新位置的原提交，而是应用了相同修改后创建的新提交。由于父提交已经改变，由提交内容、父提交和元数据共同计算出的 ID 也会随之改变。随后在 `main` 上执行 `git merge feature`，通常只需 fast-forward：

```text
A---B---C---D---E'---F'  main, feature
```

因此，rebase 得到的历史更加线性，但代价是重写了 `feature` 上的提交身份，也隐藏了它最初从 `B` 分叉这一事实。完整机制见 [Git Branching - Rebasing](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)。

## 仓库里应该保存什么

判断标准不应是“目录里现在有什么”，而应是“哪些内容属于团队共同维护，并且能够用来重建项目的状态”。

![从失败经验与矛盾状态中理解版本管理最佳实践](files/slides/版本管理（1）-slides.pdf#page=16&rect=0,0,960,540)

- 源码、测试、接口、构建脚本和必要配置通常应提交。
- 构建产物、运行日志和临时文件通常不提交，因为它们可以重新生成，也容易与源码不一致。
- 个人绝对路径与私人偏好通常不提交。团队共享且可移植的配置可以有意保留。
- 密钥和访问凭据不能提交。
- 依赖锁文件虽然由工具生成，却常用于固定版本，通常有保存价值。
- 某些项目会有意保存生成的头文件或发布产物，因此规则必须结合项目用途判断。

![判断文件是否提交，应追问它是项目输入还是可重建的产物](files/slides/版本管理（1）-slides.pdf#page=17&rect=0,0,960,540)

![仓库中常见的提交与忽略规则](files/slides/版本管理（1）-slides.pdf#page=18&rect=0,0,960,540)

`.gitignore` 把忽略规则写进项目，但不会让已经被跟踪的文件自动退出版本管理，也不会删除历史，见 [`gitignore` 文档](https://git-scm.com/docs/gitignore)。如果密钥已经进入历史，仅删除当前文件并不等于收回泄漏内容。应先撤销或轮换凭据，再根据影响范围处理历史，见 [GitHub 的敏感数据处理指南](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。

## 把一次修改组织成原子变更

原子变更是围绕一个明确意图组织起来的一组完整修改。它不一定只涉及一个文件，规模也不一定很小，但应当能够被单独解释、验证和撤销。

好的提交通常具备这些特点：

- 修复代码与对应的回归测试放在一起。
- 与本次目标无关的格式化或重构另开提交。
- 每一步尽量能够构建和测试。
- 提交说明解释行为变化和原因，diff 负责展示具体改法。
- 及时保存检查点，不让重要工作长期只存在于工作区。

提交说明可以采用 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) 的结构。

![提交说明应记录行为变化与理由](files/slides/版本管理（1）-slides.pdf#page=24&rect=0,0,960,540)

`fix` 表示变更类型，`parser` 表示范围，后面说明行为变化。正文还应解释触发条件、设计理由和相关 issue。稳定结构便于浏览和自动分类，但真正的目标仍是让后来的人理解“为什么改”和“哪些行为必须保留”。更多实践见 [Git Best Practices](https://sethrobertson.github.io/GitBestPractices/)。

清晰的原子变更还能让下面这些历史操作更可靠：

- `git bisect` 通过在一段提交历史中反复二分并测试，定位最早引入问题的提交。
- `git revert` 创建一个抵消指定提交的新提交，在不改写已有历史的情况下撤销其修改。
- `git cherry-pick` 把指定提交引入的修改应用到当前分支，并在当前起点上创建一个新提交。
- `git blame` 显示文件各行最后由哪个提交修改，帮助找到相关变化及其上下文，而不是用来追究责任。

线性历史便于阅读，但历史是否有价值，最终仍取决于每一步是否有明确意图和验证证据。

![通过及时提交与可检验的原子变化为错误留下恢复路径](files/slides/版本管理（1）-slides.pdf#page=25&rect=0,0,960,540)

![通过稳定共同依赖和自动化约束让协作过程可预期](files/slides/版本管理（1）-slides.pdf#page=26&rect=0,0,960,540)
## 从修改代码到完成工程任务

真实的软件工程任务通常遵循下面的反馈回路：

> 理解现象 → 复现问题 → 找到调用路径与项目约定 → 修改 → 验证 → 检查 diff → 提交与审查 → 集成交付

[SWE-bench](https://arxiv.org/abs/2310.06770) 使用真实的 GitHub issue 及其修复来构造任务。具体评测方式见 [SWE-bench Harness](https://www.swebench.com/SWE-bench/api/harness/)。

![SWE-bench：修复问题并守住已有行为](files/slides/版本管理（1）-slides.pdf#page=27&rect=0,0,960,540)

因此，“只改一行”只描述最终 diff 的大小，不代表工程工作只有一行。Git 保存和传输版本，GitHub CLI 的 [`gh`](https://cli.github.com/manual/) 与 GitLab CLI 的 [`glab`](https://docs.gitlab.com/cli/) 则进一步连接 issue、PR 或 MR、审查和 CI 状态。

![Git 之外还需要连接 issue、审查与 CI 的协作工具](files/slides/版本管理（1）-slides.pdf#page=29&rect=0,0,960,540)

## Agent 时代的版本管理

Agent 提高了代码产量，却没有自动消除理解、验证和集成成本。因此，可行的协作方式仍然是：

- 架构阶段先收敛接口、不变量和验收标准，把共同前提写进文档、规则和示例。
- 实现阶段把任务拆成边界清晰、尽量不冲突的变更，再并行处理。
- 每轮产出立即检查，不让未经确认的设计选择持续积累。
- 一项变更对应一个意图，并保留验证与恢复手段。

![Agent 项目的架构设计与有限并发](files/slides/版本管理（1）-slides.pdf#page=31&rect=0,0,960,540)

如果 Agent 的产能继续提高，瓶颈会从“写出修改”转向“判断哪些修改可以被接受”。未来的版本管理可能更强调快照、变更和 **change algebra**，即变更之间的组合规则。两项在文本上互不冲突的修改，组合后仍可能破坏项目不变量。

![代码产能暴涨后，等待验证和准入的变更成为新瓶颈](files/slides/版本管理（1）-slides.pdf#page=32&rect=0,0,960,540)

![在快照上并行工作，在发布时决定顺序](files/slides/版本管理（1）-slides.pdf#page=33&rect=0,0,960,540)

例如，项目要求至少一名值班员在岗。Agent A 根据旧快照让甲离岗，Agent B 根据同一快照让乙离岗。两项修改位于不同文件，文本合并没有冲突，组合后却无人值班。这与数据库中的 write skew 类似，说明快照和局部测试之外还需要验证组合结果，见 [PostgreSQL 事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)。

一种可能的流程是：

1. 每个 Agent 在独立快照上生成并测试变更。
2. 系统把变更与当前主线组合，验证候选结果。
3. 发布时确认主线仍是验证所依据的版本。
4. 如果主线已变化，就重新组合并验证。
5. 只有验证过的确切版本才能原子地进入主线。

[Jujutsu](https://docs.jj-vcs.dev/latest/tutorial/) 已经体现出一些以“变更”为中心的设计，例如稳定的 change ID、[一等冲突](https://docs.jj-vcs.dev/latest/conflicts/) 和 [operation log](https://docs.jj-vcs.dev/latest/operation-log/)。不过，无论工具怎样变化，人的关键责任仍是定义意图、不变量和验收标准，并持续追问：系统凭什么接受这次变更，还有哪些约束尚未被表达？

![以变更为中心的 Jujutsu 与 write skew](files/slides/版本管理（1）-slides.pdf#page=34&rect=0,0,960,540)

![验证越强、恢复越便宜，Agent 才越适合以更大的步幅推进](files/slides/版本管理（1）-slides.pdf#page=35&rect=0,0,960,540)
