## 从文件集合到软件工程制品

一个项目通常表现为一棵目录树，其中包含 Intent、Spec、Code、测试、配置、文档和生成结果。这些在开发过程中产生并持续维护的对象，可以统称为软件工程制品，也就是 artifact。

![项目由多种软件工程制品组成](files/slides/版本管理（2）-slides.pdf#page=2&rect=0,0,960,540)

文件是一种非常成功的通用接口。人可以阅读和编辑，程序可以搜索、比较、编译与打包，Git 也能直接管理。不过，项目本身并不天然等同于文件。文件系统擅长保存内容，却不擅长直接表达制品之间的关系。

例如，“记住用户纠正过的偏好”可能对应一项需求、一条规格、一个更新记忆的函数和若干测试。如果需求进一步变为“部分偏好只在特定时间内有效”，我们真正想知道的是：

- 哪条设计假设受到了影响？
- 哪些实现需要修改？
- 哪些测试必须增加或重写？
- 某段代码最初服务于什么需求？

这些从需求延伸到设计、实现和验证，并能从代码反查需求的联系，构成 **traceability（可追踪性）**。它关注的是能否识别并持续维护制品之间的关系，相关综述见 [Software Traceability: Trends and Future Directions](https://dl.acm.org/doi/10.1145/2593882.2593891)。

![文件不擅长直接表达制品间的可追踪关系](files/slides/版本管理（2）-slides.pdf#page=3&rect=0,0,960,540)

把文件放在同一目录中，不会自动建立可追踪性。保存所有文件版本，也不会自动解释某项设计为何存在。今天通常使用需求编号、文档链接、提交说明和测试名称来标注这些关系。它们必须持续维护，否则代码已经发生变化，旧解释却仍停留在原处。

从压缩包、SVN 到 Git，版本管理工具一直围绕文件演化，这是一种路径依赖。文件未必是表达软件的终极抽象，但围绕它形成的生态极其成熟。如果 Agent 成为软件的主要生产者和使用者，未来的系统也许会把需求、证据、实现及其相互关系直接纳入基本模型，而不再只记录“内容位于哪个文件”。

![基于文件的工具生态与 AI 时代的软件形态](files/slides/版本管理（2）-slides.pdf#page=4&rect=0,0,960,540)

## 从快照理解分叉与合并

Git 管理文件内容、目录树、项目快照，以及快照之间的历史关系。一次 commit 指向一个项目状态，同时记录父提交、作者和说明等元数据。父提交把各个状态连接起来，形成一张有向无环图。

![Git 管理文件、目录、快照及快照关系](files/slides/版本管理（2）-slides.pdf#page=5&rect=0,0,960,540)

从状态 A 出发完成一个功能，得到状态 B，可以用 `feat: ...` 说明这一步想实现什么。两个人都从 A 出发，就会形成两条不同的路线：

- merge 汇合两边的状态与历史，通常产生同时连接两条路线的新提交。
- rebase 把一条路线的改动依次重放到新的起点，让它们看起来基于新起点完成，见 [Git Branching - Rebasing](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)。

冲突意味着两条路线对共同状态作出了无法直接兼容的修改。工具可以发现文本差异，却不能替我们决定最终需要哪种行为。即使两项修改位于不同文件并且能够自动合并，组合后的结果仍可能破坏共同假设。因此，解决冲突最终需要回到需求和不变量，而不能只看冲突标记。

理解工具时，应当从它要解决的问题出发，再构造最小场景来验证自己的解释。可以亲自制造分叉、冲突和历史重写，观察工作区、提交图和引用分别发生了什么。学习的目标是形成自己的理解，而不是把课堂或考试范围误当作知识边界。

![学习的目标是形成自己的第一性理解](files/slides/版本管理（2）-slides.pdf#page=6&rect=0,0,960,540)

## 把 Change 作为一等对象

使用 `cherry-pick` 和 `rebase` 时，我们通常认为自己在移动或重放“同一项修改”。但 Git 主要使用 commit 标识这项修改。Commit 的身份与快照、父提交和元数据相关，父提交一旦改变，重写就会创建新的 commit，并产生新的 ID。

于是需要区分两个问题：

- **版本的身份**：项目在某个时刻的准确状态是什么？
- **变化的身份**：同一项修改在反复修订和改变基础后，经历了哪些版本？

![重新设计版本管理时，我们真正想操作的是 change](files/slides/版本管理（2）-slides.pdf#page=7&rect=0,0,960,540)

[Jujutsu](https://www.jj-vcs.dev/latest/) 将 change 纳入基本模型。Commit ID 标识某个具体版本，change ID 则用于追踪一项持续演化的改动。Rebase 后，commit ID 会改变，change ID 通常保持不变。换句话说，同一项修改可以拥有多个修订版本，参见 [Jujutsu 术语与设计说明](https://github.com/jj-vcs/jj/blob/main/docs/tutorial.md)。

![Jujutsu 用 change ID 延续修改的身份](files/slides/版本管理（2）-slides.pdf#page=8&rect=0,0,960,540)

Jujutsu 还将工作副本对应到一个可以继续修订的 commit。执行大多数命令时，它会自动把文件变化保存为新快照，使用体验接近持续执行 commit 与 amend，不再把独立的暂存区作为日常操作的中心，见 [Working Copy](https://github.com/jj-vcs/jj/blob/main/docs/working-copy.md)。

另一个关键设计是**把冲突保存为状态**。Rebase 遇到冲突时，Jujutsu 可以先完成历史重写，把冲突的逻辑表示记录到 commit 中，之后再统一解决。带冲突的 commit 仍然可以继续 rebase 或 merge，参见 [First-class Conflicts](https://www.jj-vcs.dev/latest/conflicts/)。

![未完成的工作和冲突都可以成为可保存的状态](files/slides/版本管理（2）-slides.pdf#page=9&rect=0,0,960,540)

> [!NOTE] 设计启发
> 当过去被视为异常或临时过程的事物，可以被明确表示、保存并继续操作时，原本割裂的流程就可能统一起来。具体工具会过时，但识别其设计前提的能力可以迁移到下一套工具。

即使新工具采用了更自然的模型，已有的肌肉记忆也可能把注意力重新锁定在旧解法上。这种现象可以用 [Einstellung effect](https://doi.org/10.1080/13546780802281154) 理解。先看清更合理的设计，再回望历史工具为什么形成今天的样子，比单纯背诵新命令更重要。

![熟悉的解法可能阻碍对更优设计的注意](files/slides/版本管理（2）-slides.pdf#page=10&rect=0,0,960,540)

## Agent 并行开发与 worktree

人类的输入输出带宽有限，同一时间通常只能专注于一个工作区，分支和 stash 已经足以支持不少任务切换。Agent 不仅能更快地产生原子修改，还能以多个实例并行工作。如果多个 Agent 直接操作同一目录，就会产生新的竞争：一个 Agent 刚读过的文件可能立刻被另一个改掉，测试尚未结束，实现也可能已经发生变化。

![面向单线程人类的工作区模型需要为 Agent 并行重新设计](files/slides/版本管理（2）-slides.pdf#page=11&rect=0,0,960,540)

![单目录无法可靠承载并行 Agent](files/slides/版本管理（2）-slides.pdf#page=12&rect=0,0,960,540)

为每个 Agent 使用独立仓库并通过 remote 同步是一种办法。在本地，[`git worktree`](https://git-scm.com/docs/git-worktree) 可以让一个仓库关联多个工作目录：

```bash
git worktree add -b agent-ui ../project-ui
git worktree add -b agent-memory ../project-memory
```

每个 worktree 都拥有自己的工作文件、`HEAD` 和暂存区，同时共享仓库对象和大部分引用。两个 Agent 可以分别运行测试，它们的新提交会直接出现在共享的本地仓库中，无需彼此 push 或 pull。不过，各自的修改最终仍须通过 merge 或 rebase 汇合。

![一个仓库通过 worktree 提供多个隔离工作目录](files/slides/版本管理（2）-slides.pdf#page=13&rect=0,0,960,540)

Worktree 解决的是工作文件相互覆盖的问题，却不会自动消除任务之间的依赖。界面需要什么数据格式、记忆模块何时提供接口、双方采用怎样的错误处理约定，仍然必须提前说明，并在集成后统一验证。

版本历史的价值也不应被简化为追责。对 Agent 团队而言，`bisect`、`blame` 和原子提交更重要的作用，是定位哪次变化破坏了什么、理解当时的上下文，以及找到可以恢复的状态。

![版本历史可以服务于定位、恢复与避免问题重演](files/slides/版本管理（2）-slides.pdf#page=14&rect=0,0,960,540)

## 先分开再合并，还是先上锁

并发协作有两条基本思路：

| 策略 | 协调时机 | 核心做法 | 主要代价 |
|---|---|---|---|
| 多版本并行 | 工作之后 | 各自在快照上推进，再 merge、rebase 和验证 | 可能产生冲突与返工 |
| 互斥锁 | 工作之前 | 修改共享状态前先取得锁，完成后释放 | 可能阻塞并行，锁范围难确定 |

Git 和 Jujutsu 可以类比为“事后”的多版本并发控制，但 Git 合并并不具备数据库事务的全部性质。另一种设计是由主 Agent 规划任务，子 Agent 在修改共享资源前先取得互斥锁：

> 上锁 → 读取最新状态 → 修改 → 验证并留下可恢复快照 → 解锁

![主 Agent 规划，子 Agent 通过锁协调共享状态](files/slides/版本管理（2）-slides.pdf#page=15&rect=0,0,960,540)

锁依赖一套所有参与者都必须遵守的协议，类似数据库的 [advisory lock](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS)。它不会自动保证修改正确，还会带来新的设计问题：

- 锁住整个项目会把并行工作重新排成串行。
- 只锁一个文件可能漏掉跨文件的不变量。
- Agent 意外停止后，锁必须能够回收。
- 同时申请多项资源可能发生死锁。
- 等待锁期间读取的状态可能已经过时，取得锁后必须重新确认。

![锁保护的应是一项工作依赖的共享状态](files/slides/版本管理（2）-slides.pdf#page=16&rect=0,0,960,540)

实际系统可以组合使用这两种策略。低冲突任务在独立快照上并行，关键共享资源通过锁来协调，最终的候选结果仍需统一验证。选择策略时，应当考虑资源范围、冲突频率、返工代价和失败后果，而不是参与者是否为 AI。

## 团队扩大后，困难转向协作

版本控制只是工具，真正困难的是让团队持续朝同一目标前进。若 $n$ 个成员都可能两两沟通，潜在关系数为：

$$
\frac{n(n-1)}{2}
$$

3 人有 3 条关系，6 人有 15 条，10 人有 45 条。这个公式只说明潜在的沟通关系会快速增长，并不意味着实际耗时一定严格按它变化。明确接口、分层组织和责任边界，正是为了减少必须直接协调的关系。相关讨论可以参考 Brooks 的[《人月神话》](https://www.cs.virginia.edu/~evans/greatworks/mythical.pdf)。

![团队规模扩大后，协调关系快速增加](files/slides/版本管理（2）-slides.pdf#page=18&rect=0,0,960,540)

常见协作失败包括：

- **目标不一致**：一方要尽快上线，另一方要趁机重构。
- **依赖在等待**：每个人都很忙，关键路径却没有推进。
- **完成定义不同**：有人认为代码写完就算完成，有人要求测试通过，还有人以为结果已经可以部署。
- **责任落在缝隙中**：接口、测试和部署各有人负责，跨模块问题却无人接手。

版本管理留下的原则是：项目不能只有当前状态，还应保留历史和教训，允许多个方向并行探索，并设计让它们重新汇合的方法。未来的 Agent Memory 也许能够记录部分经验，但什么值得记住、哪些经验已经过时、怎样为下一次决策提供支持，仍然是需要设计的问题。

![版本控制留下的是管理历史、探索与汇合的基本原则](files/slides/版本管理（2）-slides.pdf#page=19&rect=0,0,960,540)

## 把 Git 的模型迁移到其他问题

版本管理的抽象可以迁移到代码之外。课程以 Pico Playground 中小学生解汉诺塔的过程为例。只保存最终盘面，无法看出学生在哪里卡住。如果把动作序列保存下来，整个解题过程就很像一段版本历史：

- commit 保存某次有意义的尝试状态。
- 父子关系连接前后步骤。
- branch 表示从某一步开始尝试另一种方法。
- diff 比较相邻尝试的变化。
- [`git notes`](https://git-scm.com/docs/git-notes/2.42.0.html) 可以把教师点评关联到某次提交，而不改动原提交。

面对这类需求，人们通常会先想到 API、关系数据库、对象存储和后台任务等通用应用架构。这些组件并没有错，但在确定方案前，还应先辨认需求本身已经包含哪些结构。这里真正重要的是分叉的尝试、相邻步骤的差异，以及对特定版本的点评，而 Git 恰好已经提供了这些能力。

![先识别问题结构，再决定是否需要完整的通用应用架构](files/slides/版本管理（2）-slides.pdf#page=20&rect=0,0,960,540)

![Git 可以复用为解题过程的版本模型](files/slides/版本管理（2）-slides.pdf#page=21&rect=0,0,960,540)

需要区分有意义的解题版本和每一次鼠标移动。前者适合使用版本管理，后者则更像事件日志。用户资料、课程关系和统计查询也可以交给数据库。关键不是强行用 Git 解决所有问题，而是从需求结构出发，判断现有工具能够承接哪一部分。

## 从零开始，用 MVP 检验设计

从零开始做产品，往往比修改成熟项目更难。成熟项目通常已经明确了用户、分层、兼容要求和测试方式。空项目的约束较少，Intent、Spec 和 Impl 之间的缺口更大，模型也更容易用默认选择填补这些空白。

![从零开始时，任何确定设计都可能固化误解](files/slides/版本管理（2）-slides.pdf#page=22&rect=0,0,960,540)

早期 prompt 对项目方向的影响尤其大。第一次描述中的“确定设计”会成为代码和后续讨论的默认前提，之后的 Agent 又会沿着现有实现继续生成。最初为了方便而作出的临时选择，可能逐渐变成 technical debt，也就是未来修改时需要额外偿还的技术债。

技术债不一定源于草率。第一版设计在当时可能完全合理，只有投入真实使用后，团队才会发现某些概念需要拆分、接口需要重组。Martin Fowler 的 [Technical Debt Quadrant](https://martinfowler.com/bliki/TechnicalDebtQuadrant.html) 说明，团队也可能因为认识不断深入，而发现旧设计已经落后。重要的是记录当初为什么作出决定、哪些前提发生了变化，以及何时应当调整结构。架构决策记录可以参考 [Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)。

![代码保存结果，决策记录保存当时的理由与教训](files/slides/版本管理（2）-slides.pdf#page=23&rect=0,0,960,540)

MVP（Minimum Viable Product，最小可行产品）是用尽可能小但能够真正使用的版本，验证最关键的假设。开始前应当先写清两个问题：

1. 这个版本要验证什么？
2. 出现什么结果，说明最初的想法错了？

![MVP 用最小可用版本验证关键假设](files/slides/版本管理（2）-slides.pdf#page=24&rect=0,0,960,540)

个人助手的第一版不必同时接管邮件、日程、浏览器和长期记忆。可以先选择一个每天都会真实发生的场景，记录一项偏好，在下一次相关任务中使用它，并允许用户随时纠正。真实使用会把“更主动”“更了解我”等模糊形容词，转化为可以讨论和验证的具体行为。

> [!NOTE] 从版本管理回到产品开发
> 保存当前可用的状态，记录历史和决策，让小版本尽早进入真实使用。当反馈暴露出对需求的误解后，再完成下一次可以验证的修改。重点不在于让第一版完美，而在于让每一步都能提供新的证据。

![早期 prompt 的确定性会持续影响项目并形成潜在技术债](files/slides/版本管理（2）-slides.pdf#page=25&rect=0,0,960,540)

## 复习清单

学完这一讲，应当能够回答：

- 为什么项目不能只被理解为文件集合？
- 什么是 artifact 与 traceability？
- Commit ID 和 change ID 分别表示什么身份？
- Jujutsu 如何表示工作副本和未解决冲突？
- 多个 Agent 共用同一目录会产生什么问题？
- `git worktree` 隔离了什么，又没有解决什么？
- 多版本并行与互斥锁分别在什么时候协调冲突？
- 锁的范围为什么不能只按正在修改的文件决定？
- 团队规模扩大后，目标、依赖、完成定义和责任可能怎样失配？
- 如何把 Git 的状态、分支和 diff 模型迁移到代码以外的问题？
- 为什么早期 prompt 容易形成技术债？
- MVP 应该验证什么，失败证据应当怎样事先定义？
